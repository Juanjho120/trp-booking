# Phase 11.4.2 — Extraordinary Refund Authorization and Consult Evidence Lock

Status: **In progress — scope corrected; UI and financial-state acceptance pending**

Date: **2026-07-29**

Last updated: **2026-07-29**

## Goal

Correct the conclusive `/consult` reconciliation lock discovered during UI-1 testing and provide an explicit, auditable extraordinary-refund path that is independent from cancellation while never exceeding the remaining captured-payment balance.

This work remains inside Phase 11.4. It does not begin Phase 11.5 or implement Phase 11.6 notifications.

## Accepted Business Decision

The cancellation policy owns only the standard cancellation refund. An extraordinary refund is a separate administrative compensation and does not require or cause cancellation.

```text
STANDARD_POLICY
- Requires a completed cancellation request.
- Requires Reservation.status = CANCELLED.
- Uses the frozen cancellation-policy amount.
- May be split across several Refund records.
- Cannot exceed either the remaining policy allowance or the remaining payment balance.

EXTRAORDINARY
- Does not require a cancellation request.
- May be authorized while Reservation.status is CONFIRMED or CANCELLED.
- May compensate an issue before arrival, during an active stay, or after cancellation.
- Does not cancel, restore, or otherwise change the Reservation lifecycle status.
- Does not consume or rewrite the standard cancellation-policy allowance.
- Requires a clear internal administrative reason.
- Cannot exceed the remaining unrefunded captured payment.
```

A confirmed reservation remains `CONFIRMED` after an extraordinary refund. A cancelled reservation remains `CANCELLED`. Only an evidence-backed approved reconciliation changes `Payment.status` to `PARTIALLY_REFUNDED` or `REFUNDED`.

## Persisted Authorization Type

`Refund.authorizationType` remains:

```text
LEGACY_UNSPECIFIED
STANDARD_POLICY
EXTRAORDINARY
```

Migration behavior remains conservative:

```text
- Existing Refund rows are LEGACY_UNSPECIFIED.
- New rows default to STANDARD_POLICY.
- LEGACY_UNSPECIFIED participates in the standard-policy committed total.
- Only explicit EXTRAORDINARY rows are excluded from the policy allowance.
- Every committed Refund type participates in the payment-balance ceiling.
```

No additional migration is required for this scope correction. `Refund.lifecycleRequestId` is already optional, so a new extraordinary refund can be linked directly to its initial `Payment` with `lifecycleRequestId = null`.

## Authorization Boundaries

### Standard path

Endpoint:

```text
POST /api/admin/reservation-lifecycle-requests/{requestId}/refunds
```

Rules:

```text
authorizationType = STANDARD_POLICY
completed cancellation request required
Reservation.status = CANCELLED
Refund.lifecycleRequestId = cancellation request ID
remaining policy allowance enforced
remaining payment balance enforced
```

The route accepts only `STANDARD_POLICY`. A client cannot use the cancellation endpoint to create an extraordinary refund.

### Extraordinary path

Endpoint:

```text
POST /api/admin/reservations/{reservationId}/refunds/extraordinary
```

Rules:

```text
authorizationType = EXTRAORDINARY
validated initial Payment required
Payment.status = APPROVED or PARTIALLY_REFUNDED
Reservation.status = CONFIRMED or CANCELLED
Refund.lifecycleRequestId = null
internal reason required
remaining payment balance enforced
cancellation policy is not evaluated or mutated
```

The server verifies that the payment belongs to the reservation and has `Payment.purpose = INITIAL_RESERVATION`. Adjustment payments are not implicitly selected as compensation sources.

## Financial Balance Contract

The server calculates independent balances inside serializable transactions:

```text
remainingStandardPolicyAmount = standardPolicyAmount
  - committed LEGACY_UNSPECIFIED/STANDARD_POLICY Refund amounts

remainingPaymentAmount = captured initial Payment amount
  - all committed Refund amounts for that Payment
```

Committed statuses remain:

```text
PENDING
PROCESSING
APPROVED
MANUAL
```

`FAILED` attempts preserve history but release their reserved balance.

Every authorization must satisfy:

```text
amount > 0
amount has at most two decimal places
amount <= remainingPaymentAmount
```

Only `STANDARD_POLICY` must additionally satisfy:

```text
amount <= remainingStandardPolicyAmount
```

## Reservation-State Contract

Refund processing never owns the stay lifecycle:

```text
CONFIRMED + extraordinary approved -> CONFIRMED
CANCELLED + standard approved      -> CANCELLED
CANCELLED + extraordinary approved -> CANCELLED
failed/uncertain refund attempt    -> Reservation status unchanged
```

A full extraordinary refund may produce:

```text
Reservation.status = CONFIRMED
Payment.status = REFUNDED
```

That combination is valid because financial compensation does not automatically cancel the stay or release availability.

## Admin UI

The reservation refund section exposes the actions independently:

```text
Authorize by policy
- Shown only when a completed cancellation has standard policy balance.

Authorize extraordinary
- Shown for CONFIRMED or CANCELLED reservations with a refundable initial-payment balance.
```

The extraordinary form:

```text
- Starts at 0.00 so the amount is deliberate.
- States that the refund is outside the cancellation policy.
- States that it does not cancel the reservation.
- Explains that it can be used as an authorized compensation.
- Requires a clear internal reason.
- Shows the remaining payment balance rather than policy balance.
```

The refund section remains visible for an active confirmed reservation when an extraordinary refund is available.

## UI-1 Consult Evidence Correction

The observed `/consult` contract returns refund movement type `Refund`, while the initial UI recognized only `2`. The corrected UI normalizes both:

```text
2
Refund
```

When matching `/consult` evidence is conclusive, the reconciliation form locks:

```text
Outcome
Verification source
Final processing mode
Provider/refund reference
```

Only the reconciliation note remains editable.

## Server-Side Evidence Lock

Disabled UI controls are not the security boundary.

When persisted diagnostics contain conclusive `/consult` evidence, the server rejects attempts to:

```text
- Switch the source to TILOPAY_PORTAL.
- Change the derived APPROVED/FAILED outcome.
- Change the exact provider reference.
- Reconcile a non-Refund/2 movement type.
- Reconcile an amount that does not match Refund.amount.
```

A conflict returns `ADMIN_REFUND_RECONCILIATION_CONFLICT` and leaves `Refund`, `Payment`, and `Reservation` unchanged. Portal fallback remains available only when consult evidence is absent or inconclusive.

## Audit Coverage

Extraordinary authorization records:

```text
Refund.authorizationType = EXTRAORDINARY
Refund.reason = normalized admin reason
AdminAuditLog.action = REFUND_EXTRAORDINARY_AUTHORIZED
AdminAuditLog.metadata.outsideCancellationPolicy = true
AdminAuditLog.metadata.reservationCancelledByRefund = false
AdminAuditLog.metadata.reservationStatus = current CONFIRMED or CANCELLED status
```

Authorization type continues through provider and reconciliation audit events. No raw provider payload, card data, credentials, or unrestricted internal values are exposed.

## Phase 11.6 Notification Requirements — Documented, Not Implemented

The notification requirements are accepted now, but implementation remains assigned to Phase 11.6 after the financial transitions are stable.

### Notification types

```text
RESERVATION_CANCELLED
ADMIN_RESERVATION_CANCELLED
REFUND_PROCESSED
ADMIN_REFUND_PROCESSED
```

### Cancellation notifications

Trigger boundary:

```text
cancellation transaction commits
-> Reservation.status = CANCELLED
-> create/reuse guest and admin EmailNotification intents in that transaction
-> commit
-> Resend delivery occurs after commit
```

Guest cancellation email:

```text
- Confirms cancellation.
- Includes reservation reference, accommodation, cancelled dates, and cancellation timestamp.
- Does not promise that a refund has been completed.
- States that any confirmed refund will arrive in a separate notification.
- Uses Reservation.preferredLocale.
```

Admin cancellation email:

```text
- Uses a dedicated administrative template.
- Includes reservation, guest, accommodation, dates, requester channel, policy snapshot, decision, approving admin, payment state, and protected admin URL.
- Clearly distinguishes cancellation confirmation from pending or unconfirmed refunds.
```

### Refund notifications

Trigger boundary:

```text
Refund reconciliation commits with Refund.status = APPROVED
-> Payment.status becomes PARTIALLY_REFUNDED or REFUNDED
-> create/reuse guest and admin EmailNotification intents in that transaction
-> commit
-> Resend delivery occurs after commit
```

No refund email is created for:

```text
PENDING
PROCESSING
provider-accepted but confirmation pending
consult evidence before reconciliation
CONSULT_NO_MATCH
CONSULT_MATCH_INCONCLUSIVE
FAILED
```

Guest refund email:

```text
- Confirms only a reconciled approved refund.
- Includes reservation reference, confirmed amount, currency, and processing date.
- May identify an extraordinary refund as an agreed compensation without exposing internal notes.
- Includes safe guidance that posting time depends on the bank/payment method.
- Excludes raw Tilopay data, card data, internal codes, and administrative notes.
```

Admin refund email:

```text
- Uses a dedicated administrative template.
- Includes Refund ID, reservation, guest, authorization type, amount, currency, internal reason, payment status transition, authorizing admin, reconciling admin, reconciliation source, safe provider reference, and protected admin URL.
- Clearly identifies partial versus full refund and standard versus extraordinary authorization.
```

### Planned persistence for 11.6

`EmailNotification` should receive optional typed links:

```text
lifecycleRequestId String?
refundId String?
```

Stable deduplication keys:

```text
reservation-cancelled/<lifecycleRequestId>/<guest-recipient>
admin-reservation-cancelled/<lifecycleRequestId>/<admin-recipient>
refund-processed/<refundId>/<guest-recipient>
admin-refund-processed/<refundId>/<admin-recipient>
```

Email delivery failure must never reverse cancellation, refund approval, payment status, reservation state, availability, or audit history. Existing Phase 10 retry, test routing, permanent deduplication, manual recovery, and safe delivery diagnostics must be reused.

## Acceptance Scenarios

```text
1. A CONFIRMED reservation with a refundable initial payment exposes extraordinary authorization.
2. An extraordinary authorization on CONFIRMED creates PENDING with lifecycleRequestId = null.
3. An approved extraordinary reconciliation changes Payment only; Reservation remains CONFIRMED.
4. A CANCELLED reservation can still receive standard or extraordinary refunds according to each path.
5. A standard request through the cancellation endpoint remains policy-bound.
6. An extraordinary amount may bypass zero/exhausted policy but never payment balance.
7. A full extraordinary refund may leave Reservation CONFIRMED and Payment REFUNDED.
8. A non-CONFIRMED/non-CANCELLED reservation is rejected.
9. An adjustment/non-initial payment cannot be used as the extraordinary source.
10. Failed extraordinary attempts release payment balance and do not change Reservation.
11. Conclusive consult evidence locks outcome/source/mode/reference in UI and backend.
12. No lifecycle email is created by 11.4.2; requirements remain documented for 11.6.
```
