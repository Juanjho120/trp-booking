# Phase 11.4.2 — Extraordinary Refund Authorization and Consult Evidence Lock

Status: **In progress — implementation prepared; UI and financial-state acceptance pending**

Date: **2026-07-29**

## Goal

Correct the conclusive `/consult` reconciliation lock discovered during UI-1 testing and add an explicit, auditable extraordinary-refund authorization path that can exceed the applied cancellation-policy allowance without ever exceeding the captured payment.

This work remains inside Phase 11.4. It does not begin Phase 11.5.

## Accepted Business Decision

The applied cancellation policy defines the standard refund allowance, but an authorized administrator may make a separate extraordinary refund decision.

```text
STANDARD_POLICY
- Uses the frozen cancellation-policy amount.
- Can be authorized in one or several partial Refund records.
- All committed standard and legacy Refund records consume the policy allowance.
- Cannot exceed the remaining policy allowance or the remaining payment balance.
- Is unavailable when the completed cancellation request already carries a separate policy-exception snapshot; that case must use the explicit extraordinary path.

EXTRAORDINARY
- Is explicitly outside the applied cancellation policy.
- Is allowed when the policy allowance is partially used, fully used, or zero.
- Requires a clear internal reason and an informational warning in the admin form.
- Does not consume or rewrite the standard policy allowance.
- Still cannot exceed the remaining unrefunded captured payment.
```

A cancelled Reservation always remains `CANCELLED`. Only an evidence-backed approved reconciliation changes the Payment to `PARTIALLY_REFUNDED` or `REFUNDED`.

## Persisted Authorization Type

`Refund.authorizationType` is added with:

```text
LEGACY_UNSPECIFIED
STANDARD_POLICY
EXTRAORDINARY
```

Migration behavior is intentionally conservative:

```text
- Existing Refund rows become LEGACY_UNSPECIFIED.
- New rows default to STANDARD_POLICY.
- LEGACY_UNSPECIFIED participates in the standard-policy committed total.
- Only explicit EXTRAORDINARY rows are excluded from the policy allowance.
- Every committed Refund type participates in the payment-balance ceiling.
```

This prevents historical rows from being silently reclassified as extraordinary or from reopening policy allowance.

## Authorization Rules

The server calculates two independent balances inside a serializable transaction:

```text
remainingStandardPolicyAmount = standardPolicyAmount
  - committed LEGACY_UNSPECIFIED/STANDARD_POLICY Refund amounts

remainingPaymentAmount = captured Payment amount
  - all committed Refund amounts
```

Committed statuses remain:

```text
PENDING
PROCESSING
APPROVED
MANUAL
```

`FAILED` attempts retain history but release both reserved balances.

Validation:

```text
STANDARD_POLICY amount <= remainingStandardPolicyAmount
EXTRAORDINARY amount ignores remainingStandardPolicyAmount
Every authorization amount <= remainingPaymentAmount
Every amount > 0 and has at most two decimal places
Payment status must be APPROVED or PARTIALLY_REFUNDED
Reservation must remain CANCELLED
Lifecycle request must be the completed cancellation request
```

An extraordinary authorization records:

```text
Refund.authorizationType = EXTRAORDINARY
Refund.reason = normalized admin reason
AdminAuditLog.action = REFUND_EXTRAORDINARY_AUTHORIZED
AdminAuditLog.metadata.outsideCancellationPolicy = true
```

The completed cancellation request keeps its original policy snapshot unchanged. Each Refund retains its own reason, so later extraordinary decisions do not erase or reinterpret earlier cancellation/refund history.

## Admin UI

The refund section exposes separate actions when their balances allow them:

```text
Authorize by policy

```

The extraordinary form:

```text
- Identifies the authorization type as Extraordinary refund.
- Starts at 0.00 so the administrator deliberately enters the amount.
- States that the refund is not part of the applied cancellation policy.
- Requires an internal reason.
- Explains that the only financial ceiling is the remaining captured payment.
```

The summary separates:

```text

Standard amount committed
Standard policy balance
Refundable payment balance

```

Each Refund card displays its authorization type.

## UI-1 Consult Evidence Correction

The observed `/consult` contract returns refund movement type `Refund`, while the first UI implementation only recognized `2`. Therefore conclusive evidence was incorrectly opened as a portal fallback and left fields editable.

The corrected UI normalizes both:

```text
2
Refund
```

When matching `/consult` evidence is conclusive, the reconciliation form locks:

```text
Outcome
Verification source
Final processing mode
Provider/refund reference
```

Only the reconciliation note remains editable.

## Server-Side Evidence Lock

Disabled UI controls are not the security boundary.

When the persisted diagnostics contain conclusive `/consult` evidence, the server rejects any request that attempts to change the source to `TILOPAY_PORTAL`. It also revalidates:

```text
- Derived APPROVED/FAILED outcome.
- Exact provider reference.
- Normalized Refund/2 type.
- Absolute amount against Refund.amount.
```

A modified source, outcome, reference, type, or amount returns `ADMIN_REFUND_RECONCILIATION_CONFLICT` and leaves Refund, Payment, and Reservation unchanged.

Portal fallback remains available only when consult evidence is absent or inconclusive.

## Acceptance Scenarios

```text
1. Conclusive accepted consult evidence locks outcome/source/mode/reference.
2. Conclusive rejected consult evidence locks outcome/source/mode/reference.
3. A modified consult source/outcome/reference is rejected server-side.
4. Multiple standard partial refunds cannot exceed the frozen policy allowance.
5. An extraordinary refund is available after the standard allowance reaches zero.
6. An extraordinary refund is available when the applied policy amount is zero.
7. Standard and extraordinary Refund totals are displayed and audited distinctly.
8. All committed Refund types together cannot exceed the captured payment.
9. A FAILED standard or extraordinary attempt releases its reserved payment balance.
10. Approved cumulative refunds set Payment to PARTIALLY_REFUNDED or REFUNDED as appropriate.
11. Reservation remains CANCELLED in every outcome.
12. Existing migrated Refund rows display as historical unspecified and remain conservative in policy calculations.
```

11.4.2 remains in progress until these scenarios pass in local/test and the final `Refund`, `Payment`, cancellation-policy snapshot, `Reservation`, and `AdminAuditLog` states are recorded.
