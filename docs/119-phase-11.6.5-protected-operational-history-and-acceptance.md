## Purpose

Provide administrators with one protected, read-only operational history for a reservation so cancellation, authorized date changes, stay extensions, holds, payments, refunds, lifecycle emails, retries, and manual recovery can be understood without reconstructing the sequence from disconnected cards.

This subphase does not create a new source of truth. The timeline is a safe projection of accepted domain records and relations from Phases 11.1–11.6.4.

## Accepted Ownership Boundaries

```text
Reservation and ReservationLifecycleRequest own stay and request state.
LifecycleRequestHold owns the independent requested-date hold.
Payment owns captured and adjustment-payment state.
Refund owns authorization, processing, reconciliation, and outcome.
EmailNotification owns delivery state, retries, source/result relations, and manual children.
AdminAuditLog supplies bounded actor/action evidence only where a typed actor is unavailable.
```

The timeline must never derive a conflicting status or overwrite a source record.

## Protected Surface

The history belongs in the authenticated reservation detail:

```text
/admin/reservations/{reservationId}
```

It is read-only and unavailable to public or unauthenticated routes. Existing purpose-built recovery controls may remain, but timeline entries cannot be edited, deleted, reordered, or used as generic mutation commands.

## Timeline Coverage

```text
reservation creation and confirmation
cancellation request creation, approval, or rejection
DATE_CHANGE and STAY_EXTENSION request creation and decision
lifecycle hold creation, release, or expiry
initial and lifecycle-adjustment Payment creation and final state
negative-difference and compensating Refund authorization and outcome
refund provider submission, consult evidence, and reconciliation
lifecycle guest/admin notification creation and terminal outcome
payment-link guest notification and admin delivery-result relation
retry attempt count and next-attempt scheduling
manual resend child and original parent relation
source guest notification and administrative delivery-result relation
relevant administrator actors and timestamps
```

## Event Shape

```text
stable event identifier
category and event type
safe localized title and description
occurred-at timestamp
status when applicable
actor name/email or System when applicable
amount and currency when applicable
request, Payment, Refund, hold, or EmailNotification reference
parent/source relation when applicable
attempt count and next retry timestamp when applicable
safe normalized error code when applicable
```

Raw JSON metadata is not rendered directly. Provider references may appear only when already classified as safe by the existing domain layer.

## Ordering and Grouping

Use deterministic descending chronological order by effective event timestamp, followed by a stable identifier tie-breaker. Related events may be visually grouped, but each record remains independently visible and no grouping may imply that an email caused a committed domain transition.

## Data and Performance Boundaries

```text
load only records belonging to the selected reservation
use explicit typed selects
avoid unbounded N+1 queries
avoid raw provider payload columns
preserve deterministic ordering
show a clear empty state when no lifecycle events exist
```

If pagination or a bounded initial window becomes necessary, the boundary must be visible and older events must remain reviewable.

## Security and Privacy

Never expose:

```text
card number, CVV, expiration, or tokenized card fields
private lifecycle-adjustment URL or encrypted handoff token
Resend API keys, sender credentials, or raw provider responses
Tilopay credentials or raw request/response payloads
authentication or cron secrets
unfiltered AdminAuditLog metadata
```

Guest email bodies are not rendered in full. Safe history fields may include intended recipient, locale, type, delivery state, safe error code, provider message ID, and retry data.

## Localization and UX

All labels, statuses, event titles, summaries, empty states, and errors must exist in Spanish and English through the existing catalogs. Native `alert`, `confirm`, and `prompt` remain prohibited. Desktop and mobile views must distinguish request, hold, payment, refund, email, and manual recovery categories without relying only on color.

## Implementation Boundary

Likely integration points are the existing reservation-detail query, its typed response, the protected detail component, and ES/EN catalogs. New helpers/components should be narrowly scoped to the operational-history projection. A new persistence table is not expected and would require explicit review.

## Acceptance Matrix

```text
1. Only an authenticated administrator can load the history.
2. No-lifecycle reservations show a bilingual empty state.
3. Cancellation request and decision events show correct status, actor, and timestamps.
4. Positive DATE_CHANGE shows request, hold, adjustment Payment, payment-link email, delivery result, and completion in order.
5. Zero DATE_CHANGE does not fabricate a hold, adjustment Payment, or refund.
6. Negative DATE_CHANGE shows completion, exact Refund authorization, and later outcome without claiming success early.
7. STAY_EXTENSION shows its request, positive adjustment path, emails, and completion.
8. Failed positive completion shows preserved original dates and compensating Refund sequence.
9. Source/result and manual parent/child notification relations are correct.
10. Retry count, next retry, SENT, terminal FAILED, and SKIPPED states render correctly.
11. Existing recovery controls work without mutating or deleting prior history.
12. Ordering is deterministic for equal or near-equal timestamps.
13. ES/EN desktop and mobile views are complete and accessible without color-only meaning.
14. No raw provider payload, private token, credential, card data, or unfiltered audit metadata is exposed.
15. npm run lint, npm run build, focused tests, and integrated Phase 11.6 acceptance pass.
```
