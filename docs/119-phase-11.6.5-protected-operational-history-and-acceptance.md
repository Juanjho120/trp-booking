## Purpose

Provide administrators with one protected, read-only operational history for a reservation so cancellation, authorized date changes, stay extensions, holds, payments, refunds, lifecycle emails, retries, and manual recovery can be understood without reconstructing the sequence from disconnected cards.

This subphase does not create a new source of truth. The timeline is a safe projection of accepted domain records and relations from Phases 11.1–11.6.4.

## Accepted Ownership Boundaries

```text
Reservation and ReservationLifecycleRequest own stay and request state.
LifecycleRequestHold owns the independent requested-date hold.
Payment owns captured and adjustment-payment state.
Refund owns authorization, processing, reconciliation, and outcome.
EmailNotification owns delivery state, retries, source/result relations, and manual children.
AdminAuditLog supplies bounded actor/action evidence only where a typed actor is unavailable.
```

The timeline never derives a conflicting domain status and never writes to a source record.

## Protected Surface

The history is rendered only inside the authenticated reservation detail:

```text
/admin/reservations/{reservationId}
```

It is read-only and unavailable to public or unauthenticated routes. Existing purpose-built recovery controls remain in their existing sections; timeline entries cannot be edited, deleted, reordered, retried, reconciled, or used as generic mutation commands.

## Implementation Summary

The reservation-detail response now includes a typed `operationalHistory` projection. A dedicated server helper loads only records belonging to the selected reservation and builds immutable events with deterministic identifiers.

The timeline covers:

```text
reservation creation, confirmation, and cancellation context
cancellation request creation, decision, completion, failure, expiry, or withdrawal
DATE_CHANGE and STAY_EXTENSION request creation, decision, completion, failure, expiry, or withdrawal
lifecycle hold creation, release, and expiry
initial and LIFECYCLE_ADJUSTMENT Payment creation and financial outcome
standard, extraordinary, negative-difference, and compensating Refund authorization and outcome
allowlisted refund provider execution, observation, consultation, and reconciliation actions
EmailNotification creation, processing, retry scheduling, SENT, FAILED, and SKIPPED outcomes
manual resend request with parentNotificationId relation
administrative delivery-result notification with sourceNotificationId relation
administrator or System actor, amount, currency, safe reference, dates, attempts, and timestamps
```

Reservations with no cancellation, date mutation, lifecycle-adjustment payment, or refund activity show the bilingual empty state instead of a synthetic lifecycle sequence. Once lifecycle activity exists, reservation creation/confirmation and initial-payment context are included to make the sequence understandable.

## Typed Event Contract

Each event contains only bounded fields:

```text
stable event identifier
category and event type
occurred-at timestamp
status when applicable
ADMIN or SYSTEM actor
primary typed reference
allowlisted typed relations
amount and currency when applicable
request type, payment purpose, or refund authorization type
notification type, intended recipient, locale, and origin
attempt count and next retry timestamp
hold expiration and email schedule when applicable
safe normalized error code
safe provider reference already owned by the domain layer
original and requested dates when applicable
```

Event order is descending by `occurredAt`; equal timestamps use the stable event identifier as the deterministic tie-breaker.

## Query and Performance Boundary

The helper performs a bounded set of explicit Prisma reads:

```text
1 Reservation projection
1 ReservationLifecycleRequest projection including its optional hold
1 Payment projection
1 Refund projection through payments belonging to the reservation
1 EmailNotification projection
1 optional AdminAuditLog projection for allowlisted Refund actions
```

There is no per-row query loop and no new persistence table. The implementation does not select:

```text
Payment.rawPayload
PaymentClientEvent.sdkPayload
Refund.rawPayload
AdminAuditLog.metadata
email HTML or plain-text bodies
private lifecycle-adjustment handoff tokens
```

## Refund Audit Allowlist

Only these action names are eligible for timeline projection:

```text
REFUND_PROVIDER_EXECUTION_STARTED
REFUND_PROVIDER_RESPONSE_OBSERVED
REFUND_PROVIDER_RESULT_UNCERTAIN
REFUND_PROVIDER_EXECUTION_FAILED
REFUND_PROVIDER_CONSULT_OBSERVED
REFUND_RECONCILED_APPROVED
REFUND_RECONCILED_FAILED
```

The query selects only audit ID, action, entity ID, timestamp, and actor name/email. Metadata is never selected or rendered.

## Security and Privacy

The timeline never exposes:

```text
card number, CVV, expiration, or tokenized card fields
private lifecycle-adjustment URL or encrypted handoff token
Resend API keys, sender credentials, or raw provider responses
Tilopay credentials or raw request/response payloads
authentication or cron secrets
unfiltered AdminAuditLog metadata
full email bodies
```

Safe history fields may include intended recipient, locale, notification type, delivery state, attempt count, provider message ID, normalized error code, and provider references already classified as safe by the accepted domain layer.
