# Phase 11.4.1 — Observed Tilopay Contract and Evidence-Based Reconciliation

Status: **Completed and accepted — cases 1–17 documented; case 18 not required; final evidence and reconciliation acceptance passed**

Date: **2026-07-24**

Last updated: **2026-07-30**

## Goal

Replace the intentionally unknown Phase 11.4 provider-response treatment with the sanitized Tilopay sandbox contract observed during cases 1–17, while preserving conservative financial-state transitions and preventing an administrator from approving a refund from unrelated or incomplete evidence.

This correction remains part of Phase 11.4. It does not begin Phase 11.5.

## Evidence Sources

The completed matrix used three evidence sources:

```text
1. Sanitized POST /api/v1/processModification output produced by scripts/observe-tilopay-modification.ts.
2. Financial-effect verification in the Tilopay merchant transaction dashboard.
3. Sanitized POST /api/v1/consult output produced by scripts/observe-tilopay-consult.ts for case 17.
```

Cases 1–16 used the first two sources. Case 17 established the `/consult` response contract using a controlled order with one successful full type-2 refund and one later rejected refund attempt.

## Observed `processModification` Contract

### Successful modification

The successful full, partial, exact-remaining, repeated-partial, sequential-duplicate, and supported type-3 cases consistently returned:

```text
HTTP status: 200
HTTP ok: true
ReasonCode: 1101
ReasonCodeDescription: Transaction is approved
transactionId: present and unique for each provider attempt
```

Portal evidence showed a negative financial amount for a processed modification.

TRP Booking therefore classifies a modification response as provider-accepted only when all of the following are true:

```text
HTTP status = 200
HTTP ok = true
responseCode = 1101
description = Transaction is approved
providerReference is present
```

A provider-accepted response does **not** immediately change `Payment`. The `Refund` remains `PROCESSING` until a matching consult or portal movement is reconciled.

### Rejected modification

The observed rejected attempts included:

| HTTP | Code | Description | Observed financial effect |
|---|---:|---|---|
| 200 | 12 | Invalid amount | Provider attempt created; no refund applied |
| 200 | 12 | Capture error | Provider attempt created; no refund applied |
| 200 | 12 | The transaction has been closed, please contact the merchant and try again | Provider attempt created; no refund applied |
| 200 | 96 | General processor error | Provider attempt created; no refund applied |
| 400 | null | Amount/order validation messages | No provider movement |
| 401 | 401 | Invalid or missing bearer message | No provider movement |
| 500 | 500 | Oops, something went wrong | No provider movement in the missing-type/key cases |

Portal evidence showed a positive amount for the rejected type-2/type-3 attempt records that were created.

For the sandbox-only admin execution path, TRP Booking now classifies:

```text
Known response code 12 or 96 with a non-approved description
or an explicit HTTP 4xx response
=> PROVIDER_REJECTED
```

A known provider rejection sets `Refund.status = FAILED`, records the bounded response/reference, and leaves `Payment` unchanged.

HTTP 5xx responses are not automatically treated as definitive provider rejection because a server failure could occur after partial processing. They remain uncertain unless a known observed rejection code is present.

### Uncertain result

The following remain uncertain:

```text
- Timeout after the modification request may have been sent.
- Network failure after the modification request may have been sent.
- HTTP 2xx response with an unknown code or description.
- HTTP 5xx response without a recognized rejected contract.
- Accepted-looking response without a provider reference.
```

Result:

```text
Refund.status = PROCESSING
Refund.failureCode = TILOPAY_REFUND_RESULT_UNCERTAIN
Payment.status = unchanged
Automatic retry = prohibited
```

The case-7 one-millisecond timeout produced no portal movement in that specific run, but the application must still treat future timeouts conservatively because it cannot prove that the request did not reach Tilopay.

## Duplicate and Idempotency Findings

### Sequential duplicate requests

Five identical sequential type-2 requests produced:

```text
- Five responseCode 1101 approvals.
- Five different transactionId references.
- Five separate refunds.
```

Tilopay therefore does not provide usable sequential request idempotency for this endpoint.

### Concurrent duplicate requests

Two identical concurrent requests produced:

```text
- One 1101 / Transaction is approved result.
- One 12 / Capture error result.
- Two distinct provider attempt references.
- Only one financial refund.
```

Both requests reached Tilopay. TRP Booking must continue to own the idempotency boundary by atomically claiming one `PENDING` Refund as `PROCESSING` before making the provider call.

## Amount Validation Findings

```text
- 0 and 0.00 were rejected before a provider movement.
- Negative amount created a rejected provider attempt with code 96.
- Three decimal places were accepted and processed by Tilopay.
- Text, comma decimal, and empty amount were rejected without movement.
```

TRP Booking intentionally keeps its stricter positive amount format:

```text
up to 8 integer digits
optional decimal point
1 or 2 decimal digits
strictly greater than zero
```

The application does not relax validation merely because Tilopay accepted `1.000`.

## Type 2 and Type 3 Findings

### Type 2

```text
- Supports full and partial refund movements.
- Supports multiple partial movements.
- Exact remaining amount completes the refund.
- Amount above remaining creates a rejected attempt and leaves the balance unchanged.
- Fully refunded orders reject an additional type-2 attempt.
```

### Type 3

```text
- On an untouched approved order, it returned the full amount.
- After a partial type-2 refund, it returned only the remaining amount.
- It did not rewrite the earlier partial movements.
- It rejected already closed, fully refunded, or already reversed orders.
- The original transaction was not visually converted into an annulled transaction in the portal.
```

Type 3 remains outside the normal TRP Booking refund workflow. Admin API execution continues to use only type 2.

## Portal Status Limitation

The Tilopay dashboard displayed modification records as `REJECTED` even when a modification returned `1101 / Transaction is approved` and moved money.

Therefore:

```text
Portal status label alone is not accepted as financial evidence.
```

For merchant-portal evidence, the relevant movement record remains:

```text
Accepted:
- responseCode 1101
- description Transaction is approved
- negative amount displayed by the portal
- matching provider reference

Rejected:
- known rejected code/description
- positive amount when an attempt record exists
- no reduction of the refundable balance
```

The API `/consult` contract is different: both approved and rejected refund records were returned with positive amount values. The amount sign is therefore a portal presentation rule, not an API reconciliation rule.

## Implementation Decisions

### `processModification` classification

The Tilopay adapter exports a centralized classifier:

```text
PROVIDER_ACCEPTED
PROVIDER_REJECTED
RESULT_UNCERTAIN
```

The admin refund service applies it as follows:

| Classification | Refund result | Payment result |
|---|---|---|
| `PROVIDER_ACCEPTED` | Remains `PROCESSING`; reference stored; confirmation required | Unchanged |
| `PROVIDER_REJECTED` | Becomes `FAILED`; rejected code/reference stored | Unchanged |
| `RESULT_UNCERTAIN` | Remains `PROCESSING`; no retry | Unchanged |

### Safe consult observation

A new safe adapter reads all bounded candidate transaction records found under common response containers:

```text
response
transactions
data
results
items
```

It exposes only:

```text
responseCode
description
providerReference
orderNumber
type
amount
currency
status
result classification
response shape
candidate count
```

No credentials, card data, or unrestricted raw payload are exposed.

### Evidence matching

A `TILOPAY_CONSULT` result becomes conclusive only when one candidate satisfies all required evidence:

```text
providerReference = Refund.providerRefundId
orderNumber matches Payment.providerReference when returned, including the observed R- prefix
type normalizes to Refund or 2
absolute amount = Refund.amount
currency matches when returned
```

Approved consult evidence additionally requires:

```text
responseCode = 1101
description = Transaction is approved
```

Rejected consult evidence requires:

```text
known rejected response code/description
```

The amount must match the authorized `Refund.amount`, but its sign is not used because `/consult` returned positive amounts for both approved and rejected refund records.

Missing, unmatched, or incomplete data is stored as one of:

```text
CONSULT_REFERENCE_MISSING
CONSULT_NO_MATCH
CONSULT_MATCH_INCONCLUSIVE
```

It never changes `Payment`.

### Protected reconciliation

For `TILOPAY_CONSULT`:

```text
- The outcome must match the server-derived consult classification.
- The provider reference must exactly match the observed candidate.
- Normalized refund type and absolute Refund amount are revalidated inside the transaction.
- The UI cannot freely switch the consult-derived outcome or reference.
```

For `TILOPAY_PORTAL`:

```text
- The outcome remains an explicit admin decision.
- A note remains mandatory.
- APPROVED requires a provider/portal reference.
- Portal evidence must follow the observed negative/positive amount rules.
```

## Admin UI Changes

```text
- Provider-accepted, provider-rejected, uncertain, and consult-inconclusive classifications are localized.
- An accepted modification reports confirmation pending instead of generic provider observation.
- A known rejected modification reports FAILED immediately.
- The consult result reports accepted, rejected, or inconclusive evidence separately.
- TILOPAY_CONSULT is selectable for reconciliation only when conclusive matching evidence exists.
- Consult-derived outcome, final mode, and provider reference are locked to the server-derived evidence.
- Portal reconciliation remains available as the manual fallback.
```

## Phase 11.4.2 UI-1 Follow-up

UI-1 testing found that the reconciliation component still required `modificationType === "2"`, although case 17 established the actual consult value `Refund`. The server already normalized both values, but the UI incorrectly opened the result as portal fallback.

Phase 11.4.2 corrects this by:

```text
- Normalizing Refund and 2 in the admin UI.
- Locking outcome, source, final mode, and provider reference when consult evidence is conclusive.
- Leaving only the evidence note editable.
- Rejecting server-side attempts to switch conclusive consult evidence to TILOPAY_PORTAL.
- Revalidating the derived result, exact reference, normalized type, and amount in the transaction.
```

The same follow-up introduces explicit extraordinary refund authorization independent from cancellation for CONFIRMED or CANCELLED reservations. See `docs/101-phase-11.4.2-extraordinary-refund-authorization-and-consult-evidence-lock.md`.

## Safe `/consult` Observation Command

Use a controlled sandbox order that already has a known successful type-2 modification:

```powershell
npm exec -- tsx scripts/observe-tilopay-consult.ts `
  --order="REAL_SANDBOX_ORDER" |
  Tee-Object -FilePath ".\sandbox-results\17-consult.json"
```

The case-17 observation was completed on 2026-07-29 and compared with the Tilopay portal.

Observed response contract:

```text
- The top-level object contains message = success, type = 200, and response = an array.
- The response array contained the original Payment and both Refund attempts.
- The successful refund appeared with type = Refund, not type = 2.
- The successful refund returned responseCode = 1101 and description = Transaction is approved.
- The rejected post-full-refund attempt returned responseCode = 12 and the transaction-closed description.
- Both refund records returned positive amount values through /consult.
- Refund order numbers used the R- prefix while still ending with the original order number.
- Each movement had its own id_tilopay/provider reference.
- The successful processModification transactionId exactly identified the successful consult candidate.
- status was not present in the observed records.
```

The candidate collector now excludes the top-level response wrapper because a financial candidate must contain a provider reference or an order-number-plus-amount identity. Reconciliation normalizes both `Refund` and `2` as refund types and does not use the amount sign.

### Case 18 decision

`consultTransactions` was not executed and is not required for the accepted sandbox contract:

```text
- /consult returned the original payment and all known refund attempts in one response.
- Successful and rejected refund attempts were separately identifiable by provider reference.
- No movement needed for reconciliation was missing.
```

Case 18 must be revisited only if a later sandbox or production observation shows that `/consult` omits a required refund movement or cannot distinguish candidates safely.

## Acceptance Closure

11.4.1 is **Completed and accepted**.

```text
- Accepted `/consult` evidence matched the exact provider reference, order, normalized Refund/2 type, amount, currency, code, and description.
- Inconclusive evidence remained non-final and preserved Payment and Reservation state.
- Conclusive evidence locked outcome, source, final processing mode, and provider reference in the UI.
- Modified outcome, source, and provider-reference requests were rejected by the server.
- Approved and failed portal fallback reconciliation passed independently.
- Reconciliation replay returned the existing result without duplicating financial effects.
- Opposite-outcome replay was rejected.
- Payment, Refund, Reservation, and AdminAuditLog transitions were verified.
```

UI-4 rejected consult evidence is accepted as a synthetic defensive scenario rather than a normal-flow requirement:

```text
- Known processModification rejection codes 12 and 96 transition directly to Refund.status = FAILED during execution response handling.
- Therefore, the normal application flow does not naturally leave a known rejected provider attempt in PROCESSING for later rejected `/consult` classification.
- The rejected consult classifier and protected reconciliation rules remain implemented for historical, imported, uncertain, or externally altered records.
```
