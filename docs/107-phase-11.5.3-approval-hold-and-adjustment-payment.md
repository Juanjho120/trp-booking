## Goal

Implement protected approval and rejection of pending `DATE_CHANGE` and `STAY_EXTENSION` requests. A positive financial difference creates an independent requested-date hold and exact adjustment payment. The guest receives an opaque payment handoff that can use the existing Tilopay SDK without exposing reservation lookup data.

This subphase does not apply the requested dates or requested pricing to `Reservation`.

## Decision Contract

```text
- Only an authenticated authorized admin can approve or reject.
- The request must still be PENDING_REVIEW and inside its 24-hour review window.
- Request.version and Reservation.updatedAt are fenced.
- The reservation must remain CONFIRMED and the property ACTIVE.
- The source INITIAL_RESERVATION payment must remain validated.
- Approval revalidates requested dates, preparation buffers, composed dependencies, calendar blocks, and active lifecycle holds while excluding only the current Reservation.
- Rejection records the decision and audit history without creating a hold or financial movement.
- Same-decision replay returns the existing result.
- An opposite decision after a final decision is rejected.
- Serializable transactions and database constraints prevent duplicate active holds or duplicated approval artifacts.
```

## Financial Branches

### Positive difference

```text
Request.status = AWAITING_ADJUSTMENT_PAYMENT
LifecycleRequestHold.status = ACTIVE
LifecycleRequestHold duration = exactly 60 minutes
Payment.purpose = LIFECYCLE_ADJUSTMENT
Payment.status = PENDING
Payment.amount = exact financialDifference
Payment.currency = request currency
Reservation remains CONFIRMED with original dates and prices
```

The hold snapshots the current property preparation days and blocks the requested range through the existing availability domain.

### Zero difference

```text
Request.status = APPROVED
No LifecycleRequestHold
No Payment
No Reservation mutation
```

Final application remains assigned to 11.5.4.

### Negative difference

```text
Request.status = APPROVED
No LifecycleRequestHold
No Payment
No Refund yet
```

Before approval, the implementation verifies that the source payment still has enough captured balance after committed refunds to return the exact absolute difference. Final date application and lifecycle refund creation remain assigned to 11.5.5.

## Independent Hold Contract

```text
Public pending-reservation hold:
- PENDING_RESERVATION_HOLD_DURATION_MINUTES = 15
- Reservation.expiresAt
- PaymentPurpose.INITIAL_RESERVATION

Lifecycle adjustment hold:
- LIFECYCLE_ADJUSTMENT_HOLD_DURATION_MINUTES = 60
- LifecycleRequestHold.expiresAt
- PaymentPurpose.LIFECYCLE_ADJUSTMENT
```

The lifecycle hold implementation does not import, alias, derive, or update the public hold constant or `Reservation.expiresAt`.

When the lifecycle hold expires:

```text
LifecycleRequestHold ACTIVE -> EXPIRED
ReservationLifecycleRequest AWAITING_ADJUSTMENT_PAYMENT -> EXPIRED
PENDING LIFECYCLE_ADJUSTMENT payments -> FAILED
Original Reservation dates/prices/status remain unchanged
Audit action = LIFECYCLE_ADJUSTMENT_HOLD_EXPIRED
```

An already approved adjustment payment is never silently downgraded during expiry. The compensating-refund path for an approved payment whose date transition cannot complete remains assigned to 11.5.5.

## Opaque Guest Payment Handoff

The admin display exposes a private path only while the request has an active hold:

```text
/reservas/ajuste/{encrypted-token}
```

The token is:

```text
- AES-256-GCM encrypted and authenticated.
- Derived from the existing validated AUTH_SECRET with a purpose-specific context.
- Bound to LIFECYCLE_ADJUSTMENT purpose.
- Bound to lifecycle request ID, hold ID, payment ID, and hold expiration.
- Revalidated against current database state before page display, SDK session creation, preflight, and telemetry.
- Used instead of the raw Reservation ID in lifecycle checkout returnData and guest redirect URLs.
- Invalid after the hold expires.
```

The public payment SDK routes accept the token as an opaque handoff value. They do not allow guest-email or reservation-ID lookup for confirmed reservations. The private page applies the reservation snapshot locale on first load while preserving the normal manual ES/EN switch afterward.

Definitively rejected attempts, or local failures that occurred before a provider reference existed, can rotate to a new exact `PENDING` adjustment payment while the same hold remains active. Ambiguous provider failures with an existing provider reference do not create a second charge attempt automatically. The SDK session returns a new payment-bound token for preflight and client telemetry. At most one approved adjustment amount is allowed.

## Tilopay Result Isolation

The existing payment-result verification remains authoritative for provider consult, amount, currency, order reference, and order-hash validation.

`confirmReservationAfterApprovedPayment` now branches by `Payment.purpose`:

```text
INITIAL_RESERVATION:
- Existing reservation-confirmation behavior remains unchanged.
- Confirmation and arrival-notification intents remain unchanged.

LIFECYCLE_ADJUSTMENT:
- Reservation must already be CONFIRMED.
- No Reservation date, price, status, confirmedAt, or expiresAt mutation.
- No reservation-confirmation or arrival email intent.
- The confirmation service reports LIFECYCLE_ADJUSTMENT_PAYMENT_APPROVED_AWAITING_COMPLETION internally; the existing generic provider-result boundary remains unchanged in 11.5.3.
- Final date transition remains assigned to 11.5.4.
```

Provider redirects for lifecycle payments return to the opaque lifecycle adjustment page instead of the new-reservation retry/success flow. Lifecycle result URLs do not append raw reservation or payment identifiers.

## Admin UI

For a pending request, the detail page provides styled `Approve` and `Reject` actions with a required decision note. No native `confirm()` is used.

For a positive approved request, the card displays:

```text
- AWAITING_ADJUSTMENT_PAYMENT state.
- 60-minute hold countdown.
- Open-payment-link action.
- Copy-private-link action.
- Adjustment payment history and decision note through the enriched request summary.
```

All visible copy is centralized in `messages/es.ts` and `messages/en.ts`.

## Acceptance Matrix

```text
1. Reject PENDING_REVIEW request -> REJECTED, decision metadata/audit, no hold/payment/mutation.
2. Approve positive request -> AWAITING_ADJUSTMENT_PAYMENT, exactly one ACTIVE 60-minute hold, exactly one exact PENDING LIFECYCLE_ADJUSTMENT payment.
3. Approve zero request -> APPROVED, no hold/payment/mutation.
4. Approve negative request with enough captured balance -> APPROVED, no hold/payment/refund/mutation.
5. Negative approval with insufficient remaining captured balance -> rejected with no state change.
6. Approval after unrelated availability conflict -> rejected, no hold/payment.
7. Same decision replay -> same result, no duplicate audit/hold/payment.
8. Opposite decision replay -> conflict.
9. Concurrent positive approvals -> one hold and one initial adjustment payment.
10. Adjustment handoff token cannot be altered, reused for another request/payment, or used after hold expiry.
11. Guest page shows exact difference, requested dates, and hold countdown without exposing lookup fields.
12. Definitively rejected or pre-provider failed attempt can create one new exact PENDING attempt while the hold remains active; ambiguous provider failures cannot auto-create another charge.
13. Approved adjustment payment remains APPROVED and does not change Reservation dates/prices/status/confirmedAt/expiresAt.
14. Approved adjustment payment creates no RESERVATION_CONFIRMED or arrival-instruction email intent.
15. Hold expiry marks hold/request/pending payment expired/failed and preserves Reservation.
16. Public reservation checkout and exactly 15-minute hold remain unchanged.
17. ES/EN admin and guest copy are equivalent.
```
