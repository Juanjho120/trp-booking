## Pending-Hold Correction Preserved

After the database pooling correction, the hosted flow exposed a separate failure at:

```text
POST /api/reservations/pending-hold
```

The root cause was transaction-client propagation: the interactive pending-hold transaction called quote/property helpers that could fall back to the global Prisma client.

The accepted correction is represented by these repository commits:

```text
f9e4703e827371d3e93c6f9ba739b535264b6893
fix(reservations): reuse transaction client for pending hold quote

4956fe08c033d0265d5400639c94d8b4927ddaf5
fix(reservations): pass transaction client through pricing
```

The final contract is:

```text
pending-hold transaction
  -> calculateReservationQuote(..., { prismaClient: transaction })
  -> getPublicAccommodationById(..., { prismaClient: transaction })
  -> transaction.property
```

Availability already accepts the same transaction client, so the pending-hold transaction no longer opens an implicit second Prisma path while the first transaction owns the serverless connection.

A targeted repository audit did not identify another confirmed interactive-transaction helper path with the same global-Prisma fallback problem in the reservation confirmation, cancellation, refund, date-mutation, lifecycle-adjustment, payment-submission, admin-calendar, preparation-buffer, or accommodation-content flows.
