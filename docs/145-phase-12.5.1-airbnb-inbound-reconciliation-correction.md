## Why 12.5.1 Exists

The first real Airbnb inbound validation exposed two assumptions in the Phase 7 importer that do not match the provider data observed in Test.

Airbnb exported both real reservations and generic unavailable ranges:

```text
SUMMARY: Reserved
SUMMARY: Airbnb (Not available)
```

The existing importer treated every non-cancelled event as an active imported booking. It therefore:

```text
created PREPARATION_BUFFER blocks around generic Airbnb unavailability
materialized composed-listing dependency AIRBNB blocks in multiple properties
```

The real Test data showed why both behaviors are unsafe.

## Provider Behavior Observed in Test

For Apartamento Blanco y Negro, the real feed contained a real reservation surrounded by provider-generated unavailable days:

```text
2026-08-14 -> 2026-08-15  Airbnb (Not available)
2026-08-15 -> 2026-08-16  Reserved
2026-08-16 -> 2026-08-17  Airbnb (Not available)
```

Airbnb identified the 14th and 16th as one-day preparation restrictions around the real reservation.

The previous TRP behavior generated another preparation day around each `Airbnb (Not available)` event, incorrectly expanding the blocked range to the 13th and 17th.

For Bungalow Refugio Perfecto, real manual unavailable ranges were also exported as `Airbnb (Not available)`. Applying TRP preparation buffers to those manual ranges incorrectly expanded availability beyond the provider dates.

## Configuration Correction During Validation

The initial Test mapping temporarily crossed the private Airbnb feeds for Bungalow Refugio Perfecto and Refugio Completo.

The environment mapping was corrected without committing any private URL. A subsequent manual sync proved the existing reconciliation behavior:

```text
previous events attached to the wrong ExternalCalendar became REMOVED
removed_at was populated
active AIRBNB/PREPARATION_BUFFER blocks linked to those removed events were soft-deleted
correct source-calendar events were imported under the intended ExternalCalendar
```

This provider-configuration incident is not the code defect addressed by 12.5.1, but it provided a useful recovery/reconciliation test.

## Corrected Import Contract

### 1. Imported events remain attached to the source property only

The importer must materialize the provider event only on the property whose `ExternalCalendar` supplied it.

```text
Airbnb Apartment event
-> AIRBNB block: black-white-apartment only

Airbnb Bungalow event
-> AIRBNB block: perfect-retreat-bungalow only

Airbnb Complete event
-> AIRBNB block: complete-retreat only
```

The importer must not call the composed-listing affected-property rule to create physical copies of the same provider event.

Composed-listing dependencies remain the responsibility of the availability service through the established blocking-accommodation rules.

This avoids the invalid transitive case:

```text
Bungalow block
-> materialized Complete block
-> Apartment reads Complete as a blocker
-> Apartment incorrectly becomes unavailable
```

### 2. Event classification is conservative

12.5.1 classifies the observed Airbnb summary:

```text
Reserved -> RESERVATION
anything else -> UNAVAILABLE
```

Comparison is trimmed and case-insensitive.

Unknown or future provider summaries are intentionally treated as `UNAVAILABLE`, not as reservations. This preserves the provider's unavailable range without inventing preparation days.

### 3. Preparation buffers are reservation-only

```text
RESERVATION
-> source AIRBNB block
-> configured TRP PREPARATION_BUFFER blocks

UNAVAILABLE
-> source AIRBNB block
-> no TRP PREPARATION_BUFFER blocks
```

This preserves the accepted TRP preparation policy around real imported Airbnb reservations while preventing double-buffering around Airbnb's own manual/configuration/preparation restrictions.

### 4. Active-event reconciliation cleans legacy artifacts

A corrected resync must repair the data created by the previous implementation without hard deletes or manual cleanup SQL.

For each active provider event, the desired state is:

```text
exactly one active AIRBNB block for the source property
zero active propagated AIRBNB copies for other properties
PREPARATION_BUFFER blocks only when the event is classified RESERVATION
only the currently desired preparation-buffer rows remain active
```

Unexpected active blocks are soft-deleted and counted as block updates.

Existing REMOVED/CANCELLED reconciliation remains unchanged.

## Database Verification After Hosted Sync

Verify active blocks:

```sql
select
    property_id,
    start_date,
    end_date,
    source,
    reason,
    external_calendar_event_id,
    parent_block_id
from trp_booking.calendar_blocks
where deleted_at is null
  and source in ('AIRBNB', 'PREPARATION_BUFFER')
order by
    property_id,
    start_date,
    end_date,
    source;
```

Expected structural rules:

```text
Every active AIRBNB block property_id matches the property of its ExternalCalendar.
Airbnb (Not available) events have no active PREPARATION_BUFFER children.
Reserved events may have the configured preparation buffers on their source property.
No physical composed-listing AIRBNB copy remains active.
```
