## Purpose

Validate that the already-accepted TRP Booking features still operate coherently when exercised through the real Internet-accessible Test deployment and the real Test integrations.

12.8 is a cross-phase regression, not a reimplementation phase.

The goal is to prove one coherent hosted journey:

```text
public discovery
-> availability
-> pending hold
-> Tilopay sandbox payment
-> confirmed direct reservation
-> transactional email
-> protected admin visibility
-> TRP availability and composed-listing effects
-> TRP outbound iCal
-> real Airbnb import
-> Airbnb -> TRP reconciliation
-> cancellation
-> standard full refund
-> lifecycle notifications
-> outbound/provider cleanup
-> final availability recovery
```

This provides stronger integration evidence than repeating every isolated Phase 8–11 matrix.

## Test-Data Safety Contract

Use one controlled test reservation only.

Preferred source property:

```text

```

Acceptable fallback if the preferred property does not have a safe range:

```text

```

Reservation shape:

```text

guest count: valid low count within property capacity
guest identity: clearly controlled test data
guest email: an inbox controlled by the owner
locale: choose one locale for the paid E2E path
check-in: at least 8 calendar days after execution
```

Why at least 8 calendar days:

```text
The approved standard cancellation policy returns 100% only at >=168 hours before check-in.
Using at least 8 calendar days avoids operating on the exact 168-hour boundary during cleanup.
```

Before creating the hold, the owner must verify that the chosen range is safe to block temporarily on the real Airbnb listing.

Do not use dates with a real guest booking, an uncertain manual commitment, or an operational maintenance dependency.
