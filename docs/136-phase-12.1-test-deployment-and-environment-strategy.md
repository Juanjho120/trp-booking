## Phase 12 Test Contract

Phase 12 deliberately reuses developer-owned infrastructure wherever it is already
working locally. It does **not** create separate Test provider accounts merely to mimic
Production ownership.

### Vercel

```text
- Create a new TRP Booking Test project.
- Use the same personal/developer Vercel account that owns the existing portfolio projects.
- Connect the existing Juanjho120/trp-booking repository.
- Keep TRP_ENVIRONMENT=test even if Vercel classifies the deployed project/environment as production.
- Attach trp-booking.juantzun.dev only after the initial Vercel deployment is healthy.
```

### Database

```text
- Test uses the exact same developer-owned Supabase/PostgreSQL database currently used by Local.
- No dedicated Test database or Supabase project is created in Phase 12.
- Local and Test therefore intentionally share application data.
```

### Email and human correspondence

```text
Resend -> reuse existing personal Local account
Sending domain -> mail.trp-booking.juantzun.dev
Zoho -> reuse existing juantzun.dev organization
Admin mailbox -> admin@juantzun.dev
Spanish alias -> reservas@juantzun.dev
English alias -> reservations@juantzun.dev
```

The existing email DNS/Zoho setup is already accepted and is not repeated in Phase 12.
No new Test MX/SPF/DKIM/DMARC or Zoho organization is required.

The application domain still requires the DNS record needed to attach
`trp-booking.juantzun.dev` to the Test Vercel project. This is application routing, not
a new email-provider configuration.

### Cloudinary

Test reuses the exact developer-owned Cloudinary account and assets used locally. No
Test-only Cloudinary account or asset migration is required.

### Tilopay

Test reuses the existing Tilopay sandbox account and credentials used by Local. Real
Production Tilopay ownership and credentials are deferred to Phase 13.

### Cron

Test receives a new `CRON_SECRET` that is not reused from Local and will not be reused
in Production. Phase 12 later validates the actual hosted scheduler/cron execution.

## Airbnb iCal Decision

Phase 12 uses real Airbnb calendar integration intentionally.

```text
Inbound:
real Airbnb listing iCal URLs -> TRP Booking Test

Outbound:
TRP Booking Test hosted .ics URL -> controlled import/validation on real Airbnb listings
```

Local and Test share the same database. The owner will control the data used during the
Airbnb validation and explicitly requested that the current model remain unchanged.
Therefore 12.1 does not add:

```text
- Reservation.environment
- separate Local/Test database rows
- iCal filtering by environment
- extra Test-only export flags
- automatic protection against Local records appearing in the Test export
```

A future change to that boundary requires an explicit new requirement.
