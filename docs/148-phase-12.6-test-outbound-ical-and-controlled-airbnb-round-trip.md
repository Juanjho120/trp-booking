## Mandatory Discovery Before Connection

The current Phase 7 export foundation cannot be connected to Airbnb unchanged.

`generateAirbnbIcalExportFeed()` currently:

```text
- resolves all blocking accommodations for the target listing
- loads active CalendarBlock rows across those properties
- converts those rows into outbound unavailable ranges without an ownership/source whitelist
```

That means provider-origin state can enter the outbound feed, including:

```text
CalendarBlock.source = AIRBNB
PREPARATION_BUFFER rows linked to ExternalCalendarEvent / imported Airbnb reservations
```

This was acceptable while the export endpoint was only an isolated foundation. It is unsafe once Airbnb imports the TRP feed.

Potential echo:

```text
Airbnb provider block
-> imported into TRP as AIRBNB
-> emitted by TRP outbound feed
-> imported back into Airbnb as external unavailability
-> exported by Airbnb again
-> imported by TRP again
```

The provider-origin block could therefore become self-reinforcing or remain stale after the original provider reason disappears.

**No TRP Test feed may be connected to Airbnb until the 12.6.1 loop-prevention gate below passes.**

## 12.6.1 — Outbound Provider-Loop Prevention and Ownership Correction

### Required outbound ownership contract

The outbound feed may contain only unavailability owned by TRP Booking.

Include:

```text
CONFIRMED direct reservations that affect the target listing
Effective TRP preparation buffers derived from those direct reservations
MANUAL_BLOCK rows that affect the target listing
MAINTENANCE rows that affect the target listing
```

Exclude:

```text
AIRBNB CalendarBlock rows
Provider-origin PREPARATION_BUFFER rows linked to externalCalendarEventId
Any provider-import artifact whose source of truth is Airbnb
Physical COMPOSED_LISTING_DEPENDENCY copies when the same effect is already derived through getBlockingAccommodationIds()
PENDING_PAYMENT holds
Expired/cancelled reservations
Soft-deleted blocks
Admin-unlocked preparation ranges
```

The existing direct-reservation preparation calculation and admin-override suppression remain valid. The correction should narrow the CalendarBlock contribution to TRP-owned sources rather than weakening availability rules.

### Required regression scenarios

Before a real Airbnb connection:

```text
1. Imported Airbnb manual block exists in TRP
   -> NOT present in TRP outbound feed

2. Imported Airbnb Reserved event + provider-linked TRP preparation rows exist
   -> provider event and provider-derived buffers NOT echoed to Airbnb

3. Confirmed direct TRP reservation exists
   -> stay range present in correct outbound feed(s)
   -> configured direct-reservation preparation range present

4. TRP manual block exists
   -> present in outbound feed(s) affected by composed-listing rules

5. TRP maintenance block exists
   -> present in outbound feed(s) affected by composed-listing rules

6. Refugio Completo direct reservation/block
   -> blocks both component outbound feeds through dynamic blocking-property lookup

7. Apartment-only TRP block
   -> appears in Apartment and Complete outbound availability
   -> does not appear in Bungalow outbound availability

8. Bungalow-only TRP block
   -> appears in Bungalow and Complete outbound availability
   -> does not appear in Apartment outbound availability
```

A dedicated validator/test should protect this ownership contract before proceeding.

### Stable outbound VEVENT identity must be frozen before Airbnb connects

The current export foundation builds each VEVENT UID using:

```text
calendar id + positional index + normalized date range + host namespace
```

The positional index is unstable. Adding or removing an earlier range can renumber later events even when those later ranges did not change. Once Airbnb imports the feed, unchanged semantic ranges should not receive a new UID merely because another event sorted before them.

12.6.1 must therefore make UID identity independent from list position. The UID should be deterministic from stable feed identity plus the normalized unavailable range (or another stable semantic key), with no positional index.

The current UID host namespace also still uses the historical `turefugioperfecto.com.gt` value while the repository's official production domain is `turefugioperfecto.com`. Freeze the permanent UID namespace before the first real Airbnb connection so a later domain cleanup does not rewrite every provider event identity.

Required UID regression:

```text
feed with ranges B and C -> capture UIDs
insert earlier range A -> B and C keep the same UIDs
remove A -> B and C still keep the same UIDs
same calendar + same normalized range -> deterministic UID across feed generations
UID namespace uses the accepted permanent Tu Refugio Perfecto domain identity
```

### Token-path logging must be observed, not assumed

The public feed uses the raw bearer token in `/api/ical/[token]`. Application code does not intentionally log the token, but 12.6 must inspect the hosted platform/runtime request logs after controlled feed access. If the raw token appears in logs, the security gate fails and the exposure mechanism must be corrected before Airbnb is configured.

## Step 9 — Remove the Controlled Signal and Prove Recovery

Release the temporary TRP manual block through the protected admin calendar.

Then:

```text
1. verify the TRP outbound feed no longer contains that TRP-owned range
2. refresh/wait for Airbnb to remove the imported external-calendar unavailability
3. manually sync Airbnb -> TRP again
4. verify any provider event representing the removed external block is reconciled/removed
5. verify the date becomes available again everywhere that no other blocker applies
```

This is the critical anti-feedback proof. A removed TRP-owned signal must not remain blocked because its previous Airbnb reflection was echoed back into the outbound feed.
