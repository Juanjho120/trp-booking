## Purpose

Final-C.2 introduces the durable persistence and typed evidence foundation required by the accepted
Final-C.1 contract without changing any pricing behavior yet.

After C.2 is applied:

```text
- Property.baseNightlyPrice remains the only runtime price source.
- Public quotes remain unchanged.
- Pending reservation creation remains unchanged.
- DATE_CHANGE pricing remains unchanged.
- STAY_EXTENSION pricing remains unchanged.
- No seasonal or LOS rule is seeded automatically.
- Historical reservations remain valid with null Final-C pricing snapshots.
```

C.3 is responsible for making the central pricing engine authoritative for public quotes and pending
reservations. C.4 owns protected admin management and overlap-safe mutations. C.5 owns lifecycle
pricing integration.

# 1. Persistence Added by C.2

C.2 adds two Property-owned rule tables and nullable pricing-evidence columns.

## SeasonalPricingRule

Prisma model/table:

```text
SeasonalPricingRule
seasonal_pricing_rules
```

Persisted fields:

```text
id              String / cuid generated by Prisma
propertyId      Property FK
name            internal label, VARCHAR(160)
startDate       DATE, inclusive charged-night boundary
endDate         DATE, exclusive charged-night boundary
nightlyRate     DECIMAL(10,2), absolute USD nightly value
isEnabled       BOOLEAN, default true
createdAt       timestamp
updatedAt       timestamp
deletedAt      nullable timestamp for soft delete
```

The rule belongs directly to the booked Property. The FK uses `ON DELETE RESTRICT`; pricing history
is not deleted through a parent hard delete.

Database checks enforce:

```text
trimmed name is not blank
startDate < endDate
nightlyRate > 0
```

An index supports the future same-property active-range lookup used by C.4:

```text
(property_id, is_enabled, deleted_at, start_date, end_date)
```

C.2 intentionally does not add a PostgreSQL range-exclusion extension. The accepted C.1 direction
keeps overlap conflict handling in the future protected admin mutation boundary using a Serializable
transaction with bounded retry. Avoiding `btree_gist` here prevents a new database-extension
requirement solely for Final-C.

## LengthOfStayPricingRule

Prisma model/table:

```text
LengthOfStayPricingRule
length_of_stay_pricing_rules
```

Persisted fields:

```text
id              String / cuid generated by Prisma
propertyId      Property FK
minimumNights   supported LOS threshold
nightlyRate     DECIMAL(10,2), absolute USD nightly value
isEnabled       BOOLEAN, default true
createdAt       timestamp
updatedAt       timestamp
deletedAt       nullable timestamp for soft delete
```

The database accepts exactly these tiers:

```text
2, 3, 4, 5, 6, 7, 15, 30
```

Database checks enforce:

```text
minimumNights belongs to the accepted tier set
nightlyRate > 0
```

A durable unique key enforces one row per Property/tier:

```text
(property_id, minimum_nights)
```

Soft-delete/disable therefore preserves the same durable tier identity instead of allowing competing
rows for the same Property and threshold.

# 3. Prospective Pricing-Evidence Columns

The migration adds nullable JSONB columns only:

```text
reservations.pricing_snapshot

reservation_lifecycle_requests.original_pricing_snapshot
reservation_lifecycle_requests.requested_pricing_snapshot
```

Prisma exposes them as:

```text
Reservation.pricingSnapshot: Json?
ReservationLifecycleRequest.originalPricingSnapshot: Json?
ReservationLifecycleRequest.requestedPricingSnapshot: Json?
```

There is deliberately no default JSON value and no migration-time backfill.

This preserves the C.1 historical boundary:

```text
- pre-Final-C Reservation rows remain authoritative through existing numeric totals
- existing lifecycle rows remain authoritative through existing numeric original/requested fields
- null means no trustworthy Final-C pricing-resolution evidence exists
- current pricing rules are never used to invent old historical evidence
```

# 4. Typed FINAL_C_V1 Snapshot Foundation

C.2 adds:

```text
types/pricing.ts
```

The file freezes reusable domain constants:

```text
FINAL_C_PRICING_SNAPSHOT_VERSION = FINAL_C_V1
TRP_STAY_PRICING_CURRENCY = USD
SUPPORTED_LENGTH_OF_STAY_MINIMUM_NIGHTS = 2,3,4,5,6,7,15,30
```

It also defines the prospective `FinalCPricingSnapshotV1` evidence shape.

Top-level evidence contains:

```text
version
currency
propertyId
checkInDate
checkOutDate
stayLengthContextNights
pricedNights
subtotalCents
totalCents
segments
```

Every newly resolved segment is discriminated as `RESOLVED_RATE` with one source only:

```text
BASE
LENGTH_OF_STAY
SEASONAL
```

### BASE evidence

```text
resolved nightly rate in cents
segment subtotal in cents
baseNightlyRateCents
```

### LENGTH_OF_STAY evidence

```text
resolved nightly rate in cents
segment subtotal in cents
ruleId
minimumNights
configuredNightlyRateCents
```

### SEASONAL evidence

```text
resolved nightly rate in cents
segment subtotal in cents
ruleId
ruleStartDate
ruleEndDate
configuredNightlyRateCents
```

### Historical extension evidence

`PRESERVED_LEGACY_STAY` is intentionally not a pricing-resolution source. It carries only the
historical date/night boundary plus persisted accepted subtotal/total cents.

That distinction is mandatory: a pre-Final-C stay must never be mislabeled as BASE, LOS or SEASONAL
when no trustworthy historical rule evidence exists.

C.3/C.5 may group adjacent nights that resolved to identical immutable evidence, but they must
preserve the accepted `[startDate, endDate)` semantics and integer-cent totals.

# 5. Migration Safety

Migration:

```text
prisma/migrations/20260826104500_final_c_2_pricing_persistence_foundation/migration.sql
```

Properties of the migration:

```text
- additive only for existing Reservation/lifecycle rows
- no UPDATE of historical reservations
- no pricing-rule seed INSERT
- no data deletion
- no base price mutation
- no environment/provider change
- no scheduler change
- no Production resource provisioning
```

The two new pricing tables begin empty. Therefore applying C.2 cannot change a quote by itself.

The migration is wrapped in one explicit transaction and follows the repository's current migration
style.

# 6. Runtime Boundary After Migration

C.2 is a persistence foundation, not a pricing-engine rollout.

The following remain intentionally untouched:

```text
current calculateReservationQuote implementation
ReservationQuote DTO
public QuoteSummary UI
pending-hold pricing calculation
DATE_CHANGE direct pricing calculation
STAY_EXTENSION direct added-night calculation
admin accommodation UI
messages/es.ts
messages/en.ts
Tilopay payment amount flow
Final-A financial summary/refund logic
```

A database row must not become active behavior until C.3/C.4 wire the accepted engine and protected
management surface.

# 7. Validation and Rollout Order

Because Local and Hosted Test intentionally share the developer-owned Supabase database, apply the
migration once to that shared database after the schema files are in place.

Recommended gate:

```text
1. Copy the complete C.2 package into the repository.
2. Run Prisma format/generation/validation.
3. Confirm migration status before deployment.
4. Apply the pending C.2 migration to the shared Local/Test database.
5. Confirm migration status is clean afterward.
6. Verify the two rule tables are empty.
7. Verify existing Reservation pricing_snapshot values are null.
8. Verify existing lifecycle original/requested pricing snapshots are null.
9. Run Final-A and Final-B regression gates.
10. Run lint/build/diff validation.
11. Commit only after every gate passes.
```

Commands:

```bash
npm run db:format
npm run db:generate
npm run db:validate
npm run db:migrate:status
npm run db:migrate:deploy
npm run db:migrate:status
npm run final-a:validate
npm run final-b:validate
npm run lint
npm run build
git diff --check
```

Expected database verification queries after migration:

```sql
SELECT COUNT(*) AS seasonal_rule_count
FROM trp_booking.seasonal_pricing_rules;

SELECT COUNT(*) AS los_rule_count
FROM trp_booking.length_of_stay_pricing_rules;

SELECT COUNT(*) AS reservation_snapshot_count
FROM trp_booking.reservations
WHERE pricing_snapshot IS NOT NULL;

SELECT COUNT(*) AS lifecycle_snapshot_count
FROM trp_booking.reservation_lifecycle_requests
WHERE original_pricing_snapshot IS NOT NULL
   OR requested_pricing_snapshot IS NOT NULL;
```

For C.2 acceptance all four counts should be `0` unless the owner has deliberately inserted C.2 test
data after migration. No test data is supplied by this package.
