## Purpose

Connect the eight approved lifecycle templates to the accepted cancellation,
date-mutation, stay-extension, and refund transitions without placing Resend or
any external provider call inside a domain transaction.

The durable contract is:

```text
Domain transition + EmailNotification intent(s) + AdminAuditLog
-> one serializable database commit
-> best-effort post-commit delivery
-> bounded retry/stale recovery when immediate delivery does not finish
```

A provider, template, routing, or retry failure may update only email-delivery
metadata. It never restores or rolls back a cancellation, date mutation, stay
extension, approved refund, or Payment financial state.

## Notification Events

| Domain result | Guest type | Admin type |
| --- | --- | --- |
| Cancellation request `COMPLETED`, Reservation `CANCELLED` | `RESERVATION_CANCELLED` | `ADMIN_RESERVATION_CANCELLED` |
| `DATE_CHANGE` request `COMPLETED`, Reservation remains `CONFIRMED` | `RESERVATION_DATES_UPDATED` | `ADMIN_RESERVATION_DATES_UPDATED` |
| `STAY_EXTENSION` request `COMPLETED`, Reservation remains `CONFIRMED` | `STAY_EXTENSION_CONFIRMED` | `ADMIN_STAY_EXTENSION_CONFIRMED` |
| Refund `APPROVED`, Payment `PARTIALLY_REFUNDED` or `REFUNDED` | `REFUND_PROCESSED` | `ADMIN_REFUND_PROCESSED` |

Each event creates one guest intent and one intent for every configured
administrative recipient. Guest locale comes from `Reservation.preferredLocale`.
Administrative locale comes from the accepted `EMAIL_ADMIN_LOCALE` contract.

## Transactional Creation Points

### Cancellation

Inside the accepted serializable cancellation decision transaction:

```text
Reservation -> CANCELLED
Lifecycle request -> COMPLETED
Pending/failed arrival instructions -> SKIPPED
Guest cancellation intent -> create or reuse
Admin cancellation intent(s) -> create or reuse
AdminAuditLog -> append notification IDs
COMMIT
```

Only after commit does the service attempt delivery.

### Zero-Difference Date Change or Extension

The existing admin decision transaction completes the date mutation without a
Payment or lifecycle hold. The guest/admin intents are inserted after the
Reservation and lifecycle request reach their accepted final state and before
that same transaction commits.

The protected decision route begins best-effort delivery after the service has
returned successfully.

### Positive Date Change or Extension

The final completion transaction runs only after the exact lifecycle-adjustment
Payment is approved and final availability succeeds. It applies the new dates
and pricing, completes the request, releases its hold, supersedes old arrival
instructions, and inserts the guest/admin lifecycle intents atomically.

The completion service attempts delivery after commit.

### Negative Date Change

The negative completion transaction applies the new dates/pricing, completes
the request, creates the exact pending lifecycle-adjustment Refund, supersedes
arrival instructions, and inserts date-update guest/admin intents atomically.

The date-update email may state that a separate refund process exists, but it
does not claim that the refund was completed. `REFUND_PROCESSED` remains a
separate later event.

### Standard and Extraordinary Refunds

The existing administrative reconciliation transaction inserts refund intents
only when it performs a fresh transition to:

```text
Refund.status = APPROVED
Payment.status = PARTIALLY_REFUNDED | REFUNDED
```

No email is created for `PENDING`, `PROCESSING`, provider-accepted-pending,
inconclusive consult evidence, or `FAILED` outcomes.

### Lifecycle-Adjustment and Compensating Refunds

The dedicated lifecycle-adjustment reconciliation workflow follows the same
approved-only boundary. It covers both:

```text
- exact negative DATE_CHANGE refund;
- exact compensating refund after an approved positive adjustment cannot finish.
```

## Durable Relationships and Deduplication

Every automatic lifecycle row keeps `reservationId` and the approved typed
source relation:

```text
Cancellation/date change/extension -> lifecycleRequestId
Refund processed -> refundId, plus lifecycleRequestId when the Refund has one
```

Permanent automatic keys remain:

```text
reservation-cancelled/{lifecycleRequestId}/{recipient}
admin-reservation-cancelled/{lifecycleRequestId}/{recipient}
reservation-dates-updated/{lifecycleRequestId}/{recipient}
admin-reservation-dates-updated/{lifecycleRequestId}/{recipient}
stay-extension-confirmed/{lifecycleRequestId}/{recipient}
admin-stay-extension-confirmed/{lifecycleRequestId}/{recipient}
refund-processed/{refundId}/{recipient}
admin-refund-processed/{refundId}/{recipient}
```

An upsert also verifies reservation ownership, relation ownership, type, locale,
and normalized recipient. A conflicting reuse fails the transaction rather than
silently attaching an intent to the wrong source.

## Post-Commit Delivery

`lib/email/lifecycle-notifications.ts` owns the lifecycle dispatcher. It:

```text
- atomically claims PENDING rows as PROCESSING;
- reloads current typed lifecycle/refund data;
- rejects or skips superseded domain outcomes;
- renders the matching 11.6.2 builder;
- sends the permanent notification key as Resend idempotency key;
- persists only normalized safe delivery diagnostics;
- schedules retry through the accepted Phase 10 policy when allowed.
```

Disabled or unavailable email configuration does not delete the durable intent.
The row remains available for the accepted cron/recovery path after delivery is
configured.

## Manual Recovery Backend

The accepted manual-resend service now supports the eight lifecycle types in
addition to reservation-confirmation types.

A lifecycle manual child:

```text
- preserves reservationId;
- preserves lifecycleRequestId and refundId;
- keeps the original type, intended recipient, and locale;
- receives its own manual-resend deduplication key and retry history;
- uses the lifecycle dispatcher for immediate delivery and cron recovery.
```

Cancellation resend requires the Reservation to remain `CANCELLED`. Date-change
and extension resend require `CONFIRMED`. Refund resend allows `CONFIRMED` or
`CANCELLED`, matching standard, extraordinary, negative-adjustment, and
compensating-refund outcomes.

The protected UI exposure and consolidated operational timeline remain assigned
to 11.6.4.

## Supersession and Failure Safety

Before rendering, the dispatcher verifies that the current database state still
matches the email event. A mismatched request type, nonterminal request, missing
relation, changed Reservation state, nonapproved Refund, or nonfinal Payment
cannot produce a misleading email.

A lifecycle row whose event is no longer current becomes `SKIPPED` with a safe
lifecycle-superseded diagnostic. Invalid template data or unsupported final
financial data becomes nonretryable `FAILED`. Transient provider errors follow
the accepted bounded retry schedule.

None of those outcomes mutates the source domain record.
