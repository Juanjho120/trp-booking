## Goal

Implement protected administrative creation of `DATE_CHANGE` and `STAY_EXTENSION` lifecycle requests using immutable original snapshots, server-calculated requested pricing, current-reservation-only availability exclusion, idempotency, stale-state protection, audit history, and a bilingual admin display.

This subphase records a request in `PENDING_REVIEW`. It does not approve or reject the request and does not mutate the reservation.

## Preserved Product and Financial Boundaries

```text
- Guests cannot mutate confirmed dates from the public website.
- Only an authenticated authorized admin can record a request.
- Reservation.id, dates, pricing, confirmedAt, and status remain unchanged.
- Reservation.status remains CONFIRMED.
- No LifecycleRequestHold is created.
- No Payment with purpose LIFECYCLE_ADJUSTMENT is created.
- No Refund is created.
- Tilopay and Resend are not contacted.
- The normal 15-minute public pending-reservation hold is unchanged.
- The future independent 60-minute lifecycle-adjustment hold remains assigned to 11.5.3.
- No PMS behavior is added.
```

## Implemented Surface

### Protected API

```text
POST /api/admin/reservations/{reservationId}/date-mutation-requests
```

The route requires an authenticated admin session and a strict Zod body:

```text
requestType: DATE_CHANGE | STAY_EXTENSION
requestedCheckInDate: YYYY-MM-DD
requestedCheckOutDate: YYYY-MM-DD
channel: EMAIL | PHONE | WHATSAPP | OTHER
requesterName: required, at most 160 characters
requesterEmail: optional valid email
requesterPhone: optional, at most 40 characters
requestNote: required, at most 2,000 characters
expectedReservationUpdatedAt: ISO timestamp
requestId: UUID
```

The client does not submit guest count, nightly rate, subtotal, fees, taxes, discounts, total, currency, or financial difference. Those values are authoritative only when calculated or read by the server.

### Admin UI

The protected reservation detail now includes a separate **Date changes and stay extensions** section.

The section provides:

```text

- Styled text inputs for YYYY-MM-DD dates without a native browser date picker
- Guest contact fields prefilled from the reservation
- Required administrative request note
- Bilingual success/error feedback through the existing snackbar

- Calculated positive, zero, or negative financial difference

```

The UI contains no approval, rejection, payment, hold, completion, or refund action in 11.5.2.

## Eligibility Validation

Creation requires all of the following:

```text
- Reservation exists.
- Reservation.status = CONFIRMED.
- confirmedAt is present and cancelledAt is null.
- Property is supported, ACTIVE, and not soft-deleted.
- Property currency equals Reservation currency.
- A validated INITIAL_RESERVATION Payment exists in APPROVED, PARTIALLY_REFUNDED, or REFUNDED financial state.
- Payment currency equals Reservation currency.
- Requested dates are a valid [check-in, check-out) range.
- Requested dates differ from the current dates.
- Requested check-out does not exceed 365 calendar days after the current America/Guatemala business date.
- No active DATE_CHANGE or STAY_EXTENSION request exists.
- No active CANCELLATION request exists.
- Reservation.updatedAt matches expectedReservationUpdatedAt.
```

A fully refunded initial payment may still establish that the reservation was validated and paid. A future negative-difference completion remains subject to the exact remaining refundable-balance validation assigned to 11.5.5.

## DATE_CHANGE Rules

A full date change requires:

```text
- The original check-in moment has not passed.
- The requested check-in moment has not passed.
- The complete requested date range is valid and available.
```

Both check-in moments use the property's configured `checkInTime` in `America/Guatemala`.

The initial flow does not move an already-started stay. During an active stay, only `STAY_EXTENSION` can be recorded.

## STAY_EXTENSION Rules

A stay extension requires:

```text
requestedCheckInDate = originalCheckInDate
requestedCheckOutDate > originalCheckOutDate
```

The request must be recorded before the current stay's check-out boundary.

Current seeded properties have no explicit `checkOutTime`. For that existing configuration, 11.5.2 uses the end of the check-out calendar day in `America/Guatemala` as the conservative flexible-checkout boundary. When a valid property `checkOutTime` is configured, that exact local time becomes authoritative.

This rule is limited to request eligibility. No dates are changed in this subphase.

## Server-Side Pricing

### Full date change

The server prices the complete requested range using the property's current `baseNightlyPrice`:

```text
requestedSubtotal = current baseNightlyPrice × requested nights
requestedCleaningFee = 0
requestedTaxes = 0
requestedDiscounts = 0
requestedTotal = requestedSubtotal
financialDifference = requestedTotal - originalTotal
pricingMode = FULL_STAY_CURRENT_PRICE
```

### Stay extension

The server preserves the original confirmed pricing and prices only added nights:

```text
addedNightsSubtotal = current baseNightlyPrice × nights from originalCheckOutDate to requestedCheckOutDate
requestedSubtotal = originalSubtotal + addedNightsSubtotal
requestedCleaningFee = originalCleaningFee
requestedTaxes = originalTaxes
requestedDiscounts = originalDiscounts
requestedTotal = originalTotal + addedNightsSubtotal
financialDifference = addedNightsSubtotal
pricingMode = ADDED_NIGHTS_CURRENT_PRICE
```

All amounts use `Prisma.Decimal` and are normalized to two decimal places.

No amount is charged or returned in 11.5.2.

## Availability Validation

The service calls the existing availability domain inside the same serializable transaction:

```text
checkAccommodationAvailability({
  accommodationId: reservation.propertyId,
  startDate: requestedCheckInDate,
  endDate: requestedCheckOutDate,
  excludeReservationId: reservation.id
})
```

`excludeReservationId` removes only the current reservation from the reservation query. As a result, its dynamic stay blocker and derived preparation buffers are excluded from the requested-range evaluation.

The following remain authoritative blockers:

```text
- Every other CONFIRMED reservation
- Every other active PENDING_PAYMENT hold
- Airbnb calendar events and their effective blocks
- Manual blocks
- Maintenance blocks
- Non-overridden preparation buffers
- Composed-listing dependencies
- Every other active, unexpired LifecycleRequestHold
```

Unavailable requests are rejected with `ADMIN_DATE_MUTATION_DATES_UNAVAILABLE`; no lifecycle request is inserted.

A successful request stores typed dates and pricing. Its bounded audit metadata records the availability validation timestamp and affected/blocking accommodation IDs. The admin summary displays that availability was valid when the request was created; approval and final completion must revalidate again in later subphases.

## Active-Request Protection

Only one active date mutation may exist per reservation across `DATE_CHANGE` and `STAY_EXTENSION`.

Active states are:

```text
PENDING_REVIEW
APPROVED
AWAITING_ADJUSTMENT_PAYMENT
```

A cancellation request in `PENDING_REVIEW` or `APPROVED` also blocks date-mutation creation.

Historical `REJECTED`, `COMPLETED`, `WITHDRAWN`, `EXPIRED`, and `FAILED` records remain visible and do not block a new request.

## PENDING_REVIEW Expiration Handling

The accepted review lifetime remains 24 hours.

The admin summary derives and displays `reviewExpiresAt = requestedAt + 24 hours`. A stale pending request is no longer considered active by the UI.

Before creating a new request, the serializable service expires stale `PENDING_REVIEW` date-mutation rows for that reservation:

```text
status = EXPIRED
expiredAt = current timestamp
failureCode = LIFECYCLE_PENDING_REVIEW_EXPIRED
version += 1
```

Each transition creates a bounded `LIFECYCLE_REQUEST_EXPIRED` audit event using the authenticated admin who initiated the new operation. A future scheduled cleanup may be added with the broader decision/hold lifecycle, but stale rows cannot block new request creation now.

## Idempotency and Concurrency

Creation uses:

```text
clientRequestId = request UUID
idempotencyKey = reservation-date-mutation/{reservationId}/{requestId}
expectedReservationUpdatedAt
serializable transaction
reservation update fence
unique clientRequestId and idempotencyKey constraints
P2002/P2034 recovery
```

Repeating the same request ID with the same normalized request returns the existing lifecycle request.

Reusing the same request ID with different type, dates, channel, requester, contact, or reason is rejected with:

```text
ADMIN_DATE_MUTATION_IDEMPOTENCY_CONFLICT
```

Concurrent creation attempts cannot both pass the reservation fence and active-request checks. One request is retained; the other receives an active/stale conflict.

## 11.5.2.1 Correction Handoff

The backend already performs current-reservation-only exclusion. The original admin implementation used free-text `YYYY-MM-DD` inputs, so it did not visually expose the same adjusted availability before submission.

11.5.2.1 replaces those inputs with an availability-aware range picker and adds a protected reservation-scoped blocked-dates endpoint. The correction does not change the accepted server quote, request persistence, financial isolation, public availability, or hold behavior.
