## Purpose

Validate that the accepted Internet-accessible Test deployment can be observed, diagnosed,
secured, and recovered safely enough to close Test validation before Phase 12.10.

12.9 is not another booking E2E and is not a Production rollout.

It verifies five operational questions:

```text
1. Can failures be detected and correlated without exposing secrets?
2. Do durable business histories contain enough safe evidence to diagnose the important workflows?
3. Does the public/auth/API surface fail closed and expose an appropriate HTTP security posture?
4. Is database/provider recovery documented and safe for the intentionally shared Local/Test environment?
5. Are remaining Production-only monitoring, backup, and scheduler obligations explicit before Phase 13?
```

# Stage G — Recovery and Incident-Response Tabletop

This is a non-destructive operator walkthrough. Do not manufacture provider outages.

## G1 — General incident sequence

For an unexpected hosted failure, verify the operator can follow this sequence:

```text
1. Identify the affected Test URL/job/business record and approximate time.
2. Capture the Vercel RequestId/log evidence while the short retention window is still available.
3. Correlate the request to durable TRP history using safe internal IDs/status/timestamps.
4. Determine whether the failure is application, database, or external-provider related.
5. Avoid blind retries for payment/refund operations.
6. Apply the domain-specific recovery path.
7. Verify final persisted state and external-provider state.
8. Run the relevant focused validators/smoke checks.
9. Record only safe evidence.
```

```text

-> verify final Payment/Refund/Reservation states independently
```

Acceptance:

```text
[ ] operator knows the existing reconciliation path
[ ] cancellation availability is not coupled to refund retry
[ ] duplicate financial movement is explicitly avoided
```

## G3 — Email scenario

Tabletop only:


## G4 — Airbnb scenario

# Remediation Rules

If an issue is found, classify it before changing code.

## Documentation/configuration-only issue

Examples:

```text
missing runbook step
unknown backup status
unclear Production monitoring carry-forward
```

Correct documentation/configuration evidence without unrelated application changes.

## Application security issue

Examples:

```text
secret in runtime/build log
secret in client response/bundle
raw provider exception returned to user
unauthorized cron execution can start
sensitive file is publicly accessible
low-risk HTTP security headers are absent and no integration constraint exists
```

12.9 cannot close until the issue is fixed, redeployed, and the affected matrix segment passes.

## CSP-specific issue

Do not solve CSP by adding broad `*` origins or by breaking the payment integration.
Inventory the actual hosted provider origins first, then implement the narrowest validated policy or
record the exact Phase 13 enforcement gate if Production-specific provider behavior prevents a safe
final policy in Test.
