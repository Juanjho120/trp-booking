## Why 12.5.1.1 Exists

The corrected 12.5.1 resync fixed the persisted Airbnb data model:

```text
Airbnb provider blocks remain on their source property only.
Airbnb (Not available) no longer generates TRP preparation buffers.
Reserved events keep the configured TRP preparation buffers.
Legacy propagated AIRBNB blocks and invalid buffers are reconciled through soft delete.
Composed-listing availability remains dynamic through the availability service.
```

Hosted validation then exposed a presentation-only issue in the admin calendar.

The availability service correctly returns every effective blocker that applies to the selected accommodation. The admin calendar rendered those records one-for-one, so a single effective unavailable day could display duplicate-looking cards/badges even when the persistence model was correct.

Observed examples:

```text
Refugio Completo, 2026-08-08 through 2026-08-11:
- inherited Airbnb block from Apartamento Blanco y Negro
- inherited Airbnb block from Bungalow Refugio Perfecto

Refugio Completo, 2026-10-26 through 2026-10-29:
- inherited Airbnb block from Apartamento Blanco y Negro
- inherited Airbnb block from Bungalow Refugio Perfecto

Apartamento Blanco y Negro, 2026-08-14 and 2026-08-16:
- Airbnb (Not available)
- TRP PREPARATION_BUFFER around the real Airbnb Reserved event
```

Those records must remain independently persisted/auditable, but the calendar should present them as one effective blocker when they represent the same visible reason for the day.

## Corrected Presentation Contract

### 1. Persistence remains unchanged

12.5.1.1 does not merge, delete, rewrite, or deduplicate database rows.

It only consolidates `AdminCalendarEntry` records for display after the server has already evaluated effective availability.

### 2. Multiple Airbnb origins become one visible blocker

When a selected day is blocked by Airbnb entries from more than one origin accommodation, the admin calendar displays one Airbnb item.

Example for Refugio Completo:

```text
Airbnb
Apartamento Blanco y Negro · Bungalow Refugio Perfecto
```

The underlying entries remain available inside the display group.

### 3. Airbnb + preparation overlap becomes one visible blocker

When the same origin accommodation has both:

```text
AIRBNB
PREPARATION_BUFFER
```

on the selected day, the admin calendar presents one combined item:

```text
Airbnb · Preparación
```

English:

```text
Airbnb · Preparation
```

This uses the already-centralized `AIRBNB` and `PREPARATION_BUFFER` copy rather than introducing hardcoded visible copy.

This is especially important for the real Airbnb reservation observed in Apartamento Blanco y Negro:

```text
2026-08-14 -> provider Not available + TRP before-check-in preparation
2026-08-15 -> Reserved
2026-08-16 -> provider Not available + TRP after-check-out preparation
```

The 14th and 16th remain blocked by both underlying reasons but show only one effective visual item.

### 4. Refugio Completo inherits the same consolidation

If the selected accommodation is Refugio Completo and the effective blocker comes from an individual accommodation, the same consolidation rule applies before rendering.

An inherited Apartment Airbnb/preparation overlap therefore appears as one inherited `Airbnb · Preparación` item instead of two cards.

### 5. Actions remain safe

Consolidated Airbnb display groups are read-only.

A grouped `Airbnb · Preparación` item does not expose the preparation-unlock action because releasing only the TRP buffer would not make the day available while the Airbnb provider block remains active.

A standalone `PREPARATION_BUFFER` entry keeps its existing admin unlock behavior.

Manual-block and preparation-override actions are otherwise unchanged.
