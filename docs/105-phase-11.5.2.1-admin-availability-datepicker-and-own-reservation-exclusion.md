## Why This Correction Exists

The complete 11.5.2 backend acceptance matrix passed, including pricing, own-reservation overlap, unrelated blockers, date boundaries, active-request protection, stale-state handling, idempotency, concurrency, 24-hour expiry, audit metadata, and unchanged Reservation/Payment/Refund/Hold state.

Two observations were reviewed:

```text
1. A positive quote did not create a Payment.
2. The admin date fields were free-text YYYY-MM-DD inputs instead of an availability-aware datepicker.
```

The first observation is expected. 11.5.2 records only a PENDING_REVIEW quote. A `Payment` with `purpose = LIFECYCLE_ADJUSTMENT` belongs to 11.5.3 after explicit approval of a positive-difference request.

The second observation requires this UI correction before 11.5.3. The backend already excluded the current Reservation while validating the requested range, but the admin could not see that adjusted availability before submitting.

## Preserved Check-Out Boundary

The accepted backend behavior remains unchanged:

```text
- When Property.checkOutTime contains a valid configured time, that local time in America/Guatemala is the extension deadline.
- When Property.checkOutTime is null, blank, or invalid, the end of the check-out calendar day in America/Guatemala is the fallback.
- The server remains authoritative even when the calendar appears selectable.
```

## Protected Availability Endpoint

The correction adds:

```text
GET /api/admin/reservations/{reservationId}/date-mutation-blocked-dates
    ?startDate=YYYY-MM-DD
    &endDate=YYYY-MM-DD
```

The route:

```text
- Requires an authenticated admin session.
- Reads reservationId from the protected route.
- Reads the accommodation from the Reservation in the database.
- Does not accept accommodationId or excludeReservationId from the client.
- Requires a CONFIRMED eligible Reservation and ACTIVE supported Property.
- Calls the existing availability domain with excludeReservationId = Reservation.id.
- Rejects ranges longer than 42 days so the read endpoint cannot be used for unbounded scans.
- Returns only bounded blocked date strings for the requested month.
- Does not expose reservation, guest, provider, payment, or internal blocker details.
```

The public `/api/availability/blocked-dates` route remains unchanged. A guest cannot submit a reservation ID to hide availability.

## Own-Reservation Exclusion Contract

For the admin calendar only, the availability query excludes blockers derived from the Reservation being changed:

```text
- Its current stay range.
- Its dynamic preparation days before check-in.
- Its dynamic preparation days after check-out.
- Its composed-listing effects when those effects are derived from the same Reservation.
```

Every unrelated blocker remains authoritative:

```text
- Other CONFIRMED reservations.
- Other active PENDING_PAYMENT reservations.
- Airbnb calendar events.
- Manual blocks.
- Maintenance blocks.
- Preparation buffers from other reservations.
- Composed-listing dependencies from other blockers.
- Active unexpired LifecycleRequestHold records.
```

Example:

```text
Current Reservation: check-in August 19, check-out August 20
Preparation days: August 18 and August 21

Admin date-change calendar:
- August 18, 19, 20, and 21 are selectable when no unrelated blocker exists.
- The same dates remain blocked in the public booking calendar while the Reservation is still CONFIRMED.
```

The exclusion is only a quote/request aid. The existing Reservation continues blocking public availability until a later completion transaction commits the accepted dates.

## Admin Datepicker Behavior

The free-text date inputs are replaced by a styled range picker that mirrors the approved public booking calendar behavior:

```text
- One-month calendar with previous/next navigation.
- Selected start, middle, and end range styling.
- Disabled and crossed-out blocked dates.
- Clear and Done actions.
- Bilingual centralized copy.
- Month-by-month protected availability loading.
- Previously loaded months remain cached for the open request dialog.
- Submission is disabled while availability is loading or when loading failed.
- The server performs the final request-creation validation again.
```

### DATE_CHANGE

```text
- The current Reservation range is selected initially.
- The admin can select a complete replacement range.
- Dates before the Guatemala business date are disabled.
- Dates after the accepted 365-day horizon are disabled.
- The current Reservation dates and its own preparation days are not disabled unless another blocker also owns them.
```

### STAY_EXTENSION

```text
- The original check-in remains fixed.
- The current stay range is shown initially, including an active stay whose check-in is already in the past.
- Only a candidate check-out after the current check-out updates the range.
- The current Reservation dates and its own preparation days remain visible/selectable for range continuity.
- Unrelated blockers and the 365-day horizon remain enforced.
- The backend still rejects an unchanged or invalid extension.
```

## Shared UI Boundary

`components/availability/availability-date-range-picker.tsx` centralizes the styled range-calendar implementation for protected availability-aware forms. It preserves the visual and interaction contract already accepted for the guest booking calendar without changing the public booking flow in this correction.

A later low-risk cleanup may migrate the existing guest form's internal calendar wrapper to this shared component. That cleanup is not required for the admin correction and must not change public availability, quote, or 15-minute pending-hold behavior.
