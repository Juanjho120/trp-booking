## Provider Contract Accepted

```text
- processModification type 2 is the TRP Booking refund operation.
- HTTP 200 alone is not success.
- Provider acceptance requires code 1101, description Transaction is approved, and a provider reference.
- Provider acceptance remains PROCESSING until evidence-backed reconciliation.
- Known codes 12 and 96 are provider rejections and become FAILED without changing Payment.
- Unknown responses, unrecognized HTTP 5xx results, and timeouts remain uncertain PROCESSING outcomes with no blind retry.
- Sequential provider calls are not idempotent; TRP Booking owns the local claim and replay boundary.
- Type 3 remains outside the normal TRP Booking refund workflow.
```

## `/consult` Contract Accepted

Case 17 established that `/consult` returns the original Payment and all known Refund attempts in one response.

Conclusive Refund evidence requires:

```text
- Exact Refund.providerRefundId/provider reference.
- Matching provider order, including the observed R- prefix behavior.
- Type normalized as Refund or 2.
- Absolute amount equal to Refund.amount.
- Matching currency when returned.
- Approved code/description or known rejected code/description.
```

Case 18 `consultTransactions` is not required because no required movement was missing from `/consult`. It must be revisited only if a later sandbox or production observation omits required movement evidence.

## Standard Refund Acceptance

```text
- Standard refunds require a completed cancellation request and Reservation.status = CANCELLED.
- They retain lifecycleRequestId and use the frozen policy snapshot.
- Multiple partial standard Refund records accumulate correctly.
- Standard and legacy committed amounts consume the policy allowance.
- Policy and captured-payment ceilings are enforced transactionally.
- FAILED attempts preserve history and release committed balances.
```

## Extraordinary Refund Acceptance

```text
- Extraordinary refunds use the dedicated reservation endpoint.
- They link directly to the validated INITIAL_RESERVATION Payment.
- New independent compensation records use lifecycleRequestId = null.
- Reservation.status may be CONFIRMED or CANCELLED.
- Authorization, execution, consultation, and reconciliation never change Reservation lifecycle status.
- Extraordinary compensation may be partial or full and may be used before arrival, during an active stay, or after cancellation.
- It may bypass zero or exhausted policy allowance but never the remaining captured-payment balance.
- Unsupported Reservation states and non-initial payments are rejected.
- FAILED extraordinary attempts release payment balance while preserving history and audit records.
```

## Security, Idempotency, and Concurrency Acceptance

```text
- Conclusive consult evidence locks outcome, source, final processing mode, and provider reference in UI and backend.
- Modified outcome, source, or reference requests return ADMIN_REFUND_RECONCILIATION_CONFLICT.
- Repeated authorization returns the existing Refund.
- Repeated execution does not send another provider request.
- Repeated same-outcome reconciliation does not duplicate the financial effect.
- Opposite-outcome reconciliation is rejected.
- Serializable transactions, atomic PENDING-to-PROCESSING claim, unique idempotency keys, and stale-state fences protect concurrent operations.
- Standard, extraordinary, and mixed concurrent authorizations never exceed Payment.amount.
```

## Financial-State Acceptance

```text
- Provider acceptance alone does not change Payment.
- Only APPROVED reconciliation changes Payment to PARTIALLY_REFUNDED or REFUNDED.
- FAILED and inconclusive outcomes leave Payment unchanged.
- Standard refunds preserve CANCELLED.
- Extraordinary refunds preserve the existing CONFIRMED or CANCELLED state.
- A full extraordinary refund may leave Payment = REFUNDED and Reservation = CONFIRMED.
- No refund transition releases active-stay availability unless a separate cancellation has already done so.
```
