## Decision

The original 12.7 plan required upgrading the Test Vercel project to Pro so the four existing jobs could be registered and observed on their real 5-minute and 30-minute schedules.

That Test-only plan is superseded.

On 2026-08-11 the owner decided that paying for Vercel Pro only to validate recurring scheduler delivery in the Test environment is not justified. The application-level cron behavior is already implemented and remains manually executable through the protected admin cron console.

Therefore:

```text
Test Vercel project
-> may remain on Hobby
-> no Vercel Cron registrations
-> no Pro requirement
-> no recurring SCHEDULED-history acceptance gate

Production Vercel project — Phase 13
-> owns real Vercel Cron registration
-> owns recurrence and SCHEDULED-trigger validation
-> owns the plan level required by the approved frequencies
```

12.7 is not considered a failed implementation. Its hosted Test scheduler requirement is intentionally removed from Phase 12 and moved to Phase 13.

## Production-Only Configuration Boundary

TRP Booking must not maintain separate Test and Production application-code branches merely to vary Vercel Cron registration.

The same codebase must be used by both environments. The configuration boundary is `TRP_ENVIRONMENT`.

Before the first Phase 13 production scheduler deployment, replace the static Vercel configuration with Vercel programmatic configuration (`vercel.ts` or another officially supported programmatic Vercel configuration form) so cron registration is generated conditionally at deployment time.

Required behavior:

```text
TRP_ENVIRONMENT=production
-> register the four approved cron jobs

TRP_ENVIRONMENT=test
-> crons = []

TRP_ENVIRONMENT=local
-> crons = []

TRP_ENVIRONMENT missing or unknown
-> crons = []
```

The boundary must fail closed. An absent or invalid environment value must never accidentally enable recurring jobs.

Conceptual contract:

```ts
const isProduction = process.env.TRP_ENVIRONMENT === "production";

export const config = {
  crons: isProduction ? APPROVED_PRODUCTION_CRONS : [],
};
```

The exact Phase 13 implementation must follow the current Vercel programmatic-configuration contract at that time and must use only one Vercel configuration file.

## Avoiding Configuration Drift

The four approved schedules already live in `lib/cron/registry.ts`.

When the production-only Vercel configuration is implemented, do not create an unvalidated second source of truth. Use one of these safe patterns:

```text
Preferred:
- move path/schedule metadata into a lightweight dependency-free configuration module
- import that module from both the application cron registry and the Vercel programmatic config

Acceptable alternative:
- keep separate Vercel registration metadata
- add an automated validator that proves every path/schedule matches the application registry
```

Do not import the full application cron registry into Vercel deployment configuration if doing so would pull Prisma, provider clients, or runtime business dependencies into configuration evaluation.
