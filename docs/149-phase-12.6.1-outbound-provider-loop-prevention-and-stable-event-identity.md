## Why 12.6.1 Is Mandatory

The Phase 7 export foundation was safe while it was not connected back to Airbnb, but its broad `CalendarBlock` contribution would be unsafe in a real bidirectional round-trip.

Before this correction, an imported provider block could follow this path:

```text
Airbnb
-> TRP AIRBNB CalendarBlock
-> TRP outbound iCal
-> Airbnb imported external-calendar unavailability
-> Airbnb export
-> TRP inbound sync
```

That can make provider-origin state self-reinforcing or leave stale unavailability after the original source disappears.

12.6.1 therefore freezes an explicit ownership boundary before any TRP Test feed is connected to a real Airbnb listing.

## Outbound Ownership Contract

The canonical TRP outbound feed now has two source categories.

### Reservation-owned unavailability

Confirmed direct reservations remain sourced from `Reservation` records:

```text
Reservation.status = CONFIRMED
-> stay range exported
-> configured preparation ranges derived dynamically
-> individual admin-unlocked preparation days suppressed
```

`CalendarBlock.source = DIRECT_RESERVATION` is not used as a second outbound source of truth.

### TRP-owned CalendarBlock unavailability

Only these `CalendarBlock` sources may contribute:

```text
MANUAL_BLOCK
MAINTENANCE
PREPARATION_BUFFER where externalCalendarEventId is null
```

The query itself applies this boundary, and `isTrpOwnedCalendarBlockForAirbnbExport()` repeats the ownership check as defense in depth before range conversion.

### Provider-origin state excluded

These records do not contribute to outbound feeds:

```text
AIRBNB
PREPARATION_BUFFER linked to externalCalendarEventId
any provider-import artifact linked to ExternalCalendarEvent
COMPOSED_LISTING_DEPENDENCY physical copies
DIRECT_RESERVATION CalendarBlock copies
soft-deleted blocks
```

The dynamic composed-listing matrix is preserved through `getBlockingAccommodationIds()` instead of exporting physical dependency copies.

## Why Direct Preparation Overrides Still Work

A direct reservation preparation day that an admin unlocks is persisted as:

```text
CalendarBlock.source = PREPARATION_BUFFER
reservationId = <direct reservation>
externalCalendarEventId = null
unlockedByAdminAt != null
```

Those rows remain available to the export service as suppression records. They remove the corresponding day from the dynamically derived direct-reservation preparation range, while `isPreparationBufferOverride()` prevents the override row itself from becoming an unavailable outbound event.

Provider-derived preparation rows have `externalCalendarEventId != null` and are excluded before they can affect a direct reservation's outbound buffer calculation.

## Composed-Listing Contract Preserved

12.6.1 does not change `getBlockingAccommodationIds()`.

Expected outbound matrix remains:

```text
TRP source: Apartment
-> Apartment feed blocked
-> Complete feed blocked
-> Bungalow feed unaffected

TRP source: Bungalow
-> Bungalow feed blocked
-> Complete feed blocked
-> Apartment feed unaffected

TRP source: Complete
-> Complete feed blocked
-> Apartment feed blocked
-> Bungalow feed blocked
```

This applies to direct reservations and export-eligible TRP-owned manual/maintenance state.

## Stable VEVENT Identity

The previous UID contained a positional array index:

```text
calendar + index + normalized range + host
```

That meant inserting an earlier unrelated range could rename later unchanged events.

12.6.1 freezes UID identity as:

```text
calendar id + normalized start date + normalized end date + permanent host namespace
```

Equivalent form:

```text
trp-booking-<externalCalendarId>-<startDate>-<endDate>@turefugioperfecto.com
```

There is no positional index.

Therefore:

```text
same calendar + same normalized range
-> same UID

insert/remove unrelated earlier range
-> existing semantic range keeps its UID
```

The permanent UID namespace is now:

```text
turefugioperfecto.com
```

The historical `turefugioperfecto.com.gt` namespace is removed before the first real Airbnb import so provider identities do not need a later mass rewrite.
