## Purpose

Add the complete bilingual HTML and plain-text template layer for the eight
approved lifecycle notification types without creating database intents or
calling Resend.

The delivery reuses the accepted Phase 10 email architecture:

```text
- branded responsive HTML layout;
- absolute public logo and application URLs;
- mandatory plain-text alternatives;
- centralized Spanish and English catalogs;
- strict typed inputs and Zod validation;
- normalized safe view models;
- EmailTemplateDataError for invalid template data.
```

## Centralized Copy Strategy

No visible copy is hardcoded in the lifecycle TSX templates.

The builders reuse the accepted bilingual catalogs from:

```text
messages/es.ts
messages/en.ts
```

The lifecycle message selector composes existing centralized namespaces:

```text
emails.common
emails.reservationConfirmed
emails.adminNewReservation
admin.navigation
admin.statuses.payment
admin.reservationsPage.cancellation
admin.reservationsPage.dateMutation
admin.reservationsPage.refunds
admin.reservationsPage.notifications
payments.lifecycleAdjustment
```

This avoids a second feature-local message source and preserves the project rule
that public, administrative, and transactional copy remains owned by the two
language catalogs.

## Guest Locale Boundary

Guest builders require:

```text
input.locale = Reservation.preferredLocale
```

A mismatch throws `EmailTemplateDataError` before rendering. Later orchestration
must therefore load the reservation locale and call the matching guest builder.

Administrative builders use the locale selected by the accepted admin email
environment contract. They do not depend on the guest locale.

## Template Data Validation

The lifecycle schemas validate and normalize:

```text
- supported es/en locale;
- reservation ID, guest identity, and normalized email;
- bilingual accommodation names;
- ISO date-only stay values;
- offset-aware lifecycle timestamps;
- nonnegative and signed two-decimal money values;
- three-letter currency;
- approved request channels and lifecycle/financial states;
- optional bounded request, decision, and refund notes;
- HTTP/HTTPS application base URL without embedded credentials;
- public HTTPS logo URL without localhost or embedded credentials.
```

Dates are formatted using Spanish Guatemala or US English locale rules. Lifecycle
timestamps use `America/Guatemala`. Stay dates use UTC date-only formatting so
they do not shift across time zones.

## Cancellation Templates

Guest cancellation output includes:

```text
- reservation reference and accommodation;
- cancelled stay dates;
- cancellation completion time;
- frozen policy reason;
- eligible percentage and amount;
- explicit separation between cancellation and refund processing;
- reservations support contact.
```

It never claims that money has already been returned.

Administrative cancellation output additionally includes bounded request
channel, request reason, creating/reviewing actors, decision note, policy result,
and a protected reservation-detail URL.

## Date-Update Templates

Guest date-update output includes:

```text
- original and confirmed new dates;
- original and new totals;
- financial difference;
- separately authorized refund amount when supplied;
- an explicit separate-refund boundary when reconciliation is not yet approved.
```

Administrative output additionally includes request channel/reason, actors,
decision note, completion time, adjustment-payment state, refund state/amount,
and the protected reservation-detail URL.

The builder represents only a `DATE_CHANGE` already completed by the lifecycle
domain. It does not decide whether dates should be applied.

## Stay-Extension Templates

Guest extension output includes:

```text
- preserved check-in;
- original and confirmed new check-out;
- added-night count;
- additional amount;
- new confirmed total.
```

Administrative output additionally includes the original total, adjustment
Payment state, normalized lifecycle-hold state, request context, actors,
completion time, and protected reservation-detail URL.

## Refund Templates

Refund builders represent only a financial result already reconciled as:

```text
Refund.status = APPROVED
Payment.status = PARTIALLY_REFUNDED or REFUNDED
```

Guest output includes the confirmed amount, authorization context, final payment
state, approval time, and the rule that the refund does not change the
Reservation lifecycle by itself.

Administrative output may additionally include processing mode, safe provider
reference, bounded reason, authorizing/reconciling actors, and protected
reservation detail.

The templates do not expose raw Tilopay payloads, credentials, headers, card
data, unrestricted provider errors, or banking-time promises.

## Shared Rendering

A shared lifecycle renderer owns:

```text
- Phase 10 EmailLayout branding;
- eyebrow, title, paragraphs, success note, and detail sections;
- optional protected admin action;
- optional guest support contact;
- equivalent plain-text sections and rows.
```

Template-specific builders prepare only safe localized view data. This avoids
eight near-duplicate layout implementations while retaining separate exported
builders and strict event inputs.

## Explicit Non-Goals

```text
- No EmailNotification row creation.
- No cancellation/date-change/extension/refund transaction hook.
- No deduplication-key use during a real transition.
- No Resend provider call.
- No retry, stale-claim, cron, test-routing, or manual-resend change.
- No protected lifecycle timeline UI.
- No Prisma schema or migration change.
- No environment variable or dependency change.
- No historical email backfill.
- No guest self-service lifecycle mutation.
- No hard deletion, card-data handling, raw provider exposure, or PMS behavior.
```

## Acceptance Matrix

The following matrix remains authoritative for the template layer. Technical
acceptance was completed in 11.6.2; visual content, real delivery, and inbox
acceptance are intentionally consolidated into the one-time integrated 11.6.3
matrix so the same cases are not executed twice.

```text
1. All eight builders compile and are exported from emails/index.ts.
2. Each builder returns subject, branded HTML, and plain text.
3. Spanish and English inputs render localized dates, amounts, and copy.
4. Guest builders reject locale/preferredLocale mismatches.
5. Admin builders render the protected reservation URL only in admin output.
6. Guest cancellation output does not promise an approved refund.
7. Admin cancellation output includes bounded policy/request context.
8. Guest date-update output includes original/new dates and totals.
9. Admin date-update output includes payment/refund/request context.
10. Guest extension output preserves check-in and shows new check-out.
11. Admin extension output includes payment, hold, actor, and request context.
12. Refund builders accept only final REFUNDED/PARTIALLY_REFUNDED payment states.
13. Guest output excludes internal notes and admin URLs.
14. Admin output excludes raw provider payloads, credentials, and card data.
15. Invalid dates, amounts, currencies, URLs, states, or oversized notes throw EmailTemplateDataError.
16. Existing confirmation and arrival template behavior remains unchanged.
17. No EmailNotification row or Resend request is made.
18. Environment validation, Prisma validation, lint, build, and diff checks pass.
```
