## Purpose

Notify the guest when an approved positive `DATE_CHANGE` or
`STAY_EXTENSION` requires an adjustment payment, expose a protected admin action
to send the same private link again, report the guest-email delivery result to
administrators, and correct the completed date-change copy for positive, zero,
and negative financial branches.

The payment-required message is intentionally earlier than the existing final
completion emails:

```text
Request approved with positive difference
-> request AWAITING_ADJUSTMENT_PAYMENT
-> active 60-minute LifecycleRequestHold
-> exact PENDING LIFECYCLE_ADJUSTMENT Payment
-> guest payment-required EmailNotification
-> payment approval and successful completion
-> final RESERVATION_DATES_UPDATED or STAY_EXTENSION_CONFIRMED email
```

The payment-required email never states that the requested dates already took
effect.

## Notification Types

```text
DATE_CHANGE_PAYMENT_REQUIRED
STAY_EXTENSION_PAYMENT_REQUIRED
ADMIN_DATE_CHANGE_PAYMENT_LINK_DELIVERY_STATUS
ADMIN_STAY_EXTENSION_PAYMENT_LINK_DELIVERY_STATUS
```

Guest automatic keys:

```text
date-change-payment-required/{lifecycleRequestId}/{recipient}
stay-extension-payment-required/{lifecycleRequestId}/{recipient}
```

Admin delivery-result keys:

```text
admin-date-change-payment-link-delivery-status/{sourceNotificationId}/{recipient}
admin-stay-extension-payment-link-delivery-status/{sourceNotificationId}/{recipient}
```

Each result email uses `sourceNotificationId` to identify the exact guest send
that reached a terminal delivery state. This relation is separate from
`parentNotificationId`, which remains reserved for manual resend chains and
continues suppressing automatic processing of replaced source rows.

## Guest Payment-Required Email

A guest intent is eligible only while all conditions remain true:

```text
request type = DATE_CHANGE or STAY_EXTENSION
request status = AWAITING_ADJUSTMENT_PAYMENT
financialDifference > 0
Reservation.status = CONFIRMED
LifecycleRequestHold.status = ACTIVE
LifecycleRequestHold.expiresAt > now
exact LIFECYCLE_ADJUSTMENT Payment exists
Payment.status = PENDING
Payment.amount = financialDifference
Payment.currency = request currency
```

The email includes:

```text
reservation reference
accommodation
current confirmed dates
requested dates
exact difference due
hold expiration in America/Guatemala
private payment button
plain-text payment URL fallback
explicit notice that the requested dates are not active yet
```

The private URL reuses the accepted encrypted lifecycle-adjustment handoff token
bound to the request, hold, payment, and expiration. The token is not stored in
EmailNotification or audit metadata.

A stale, paid, expired, completed, rejected, or otherwise nonpayable request is
marked `SKIPPED` before rendering rather than sending a misleading link.

## Automatic Creation and Recovery

After a positive admin approval commits, the protected decision route creates or
reuses the durable guest intent and attempts delivery. No provider call runs
inside the approval transaction.

The Phase 10 worker also reconciles payable requests that do not yet have the
guest intent. This closes the small post-commit interruption window between the
successful domain commit and intent creation without creating historical
backfill for already completed or expired requests.

Permanent deduplication makes route replay, worker recovery, and concurrent
execution resolve to one automatic guest intent per request and recipient.

## Administrative Delivery-Result Email

Each configured administrator receives a separate result intent after the exact
guest payment-link notification reaches one of these terminal outcomes:

```text
SENT
-> Resend/provider accepted the message from TRP Booking
-> does not prove inbox delivery, opening, or reading

FAILED with nextAttemptAt = null
-> delivery ended without another scheduled automatic retry
```

A retryable intermediate failure does not generate the administrative failure
email. The result is created only after the retry lifecycle becomes final.

The administrative message includes only bounded operational context:

```text
reservation reference
guest name
request type
intended guest recipient
source EmailNotification ID
attempt count
observed timestamp
safe normalized error code when failed
protected reservation-detail link
```

No raw Resend payload, API key, sender credential, Tilopay payload, private
payment token, or card data is included.

An administrative result-email failure uses the normal bounded retry pipeline
and never creates another email reporting its own failure.

## Protected Manual Send Action

The existing positive-adjustment controls now show, beside the open and copy
actions:

```text
Send payment link by email
```

The button remains visible while the private link is usable: the request is
awaiting adjustment payment, the exact Payment is pending, and the hold is
active and unexpired.

Before sending, a protected GET endpoint returns the current delivery state.
The Radix Sheet displays:

```text
any SENT row
-> duplicate warning

PENDING, PROCESSING, or retryable FAILED row
-> active-delivery warning

FAILED rows with no successful or active delivery
-> no duplicate warning; failed-delivery information only
```

The POST action uses a browser-generated UUID. A previously sent or failed leaf
creates an auditable MANUAL child with:

```text
manual-resend/{sourceNotificationId}/{requestId}
```

A current PENDING leaf is claimed directly instead of creating an unnecessary
copy. A retryable FAILED source replaced by a manual child stops automatic
processing through the accepted `manualResends: { none: {} }` rule.

The original row and every previous delivery attempt remain unchanged.

Protected endpoint:

```text
GET  /api/admin/reservations/{reservationId}/date-mutation-requests/{requestId}/payment-link-email
POST /api/admin/reservations/{reservationId}/date-mutation-requests/{requestId}/payment-link-email
```

## Completed Date-Change Copy

`RESERVATION_DATES_UPDATED` now selects its introduction from the persisted
financial difference:

```text
POSITIVE
The additional payment was validated and the requested dates were applied.

ZERO
The requested dates were applied without mentioning an additional payment.

NEGATIVE
The requested dates were applied, and refund confirmation will be sent
separately after the refund process is completed.
```

The negative message does not promise that the refund will arrive "soon".
`REFUND_PROCESSED` remains the only email that confirms a completed refund.

## Retry and Failure Safety

All four new types reuse:

```text
PENDING -> PROCESSING atomic claim
processingStartedAt ownership token
maximum 5 attempts
5m / 15m / 1h / 6h retry schedule
10-minute stale PROCESSING recovery
Resend idempotency key = permanent EmailNotification key
test-recipient routing
normalized safe diagnostics
```

A template, provider, routing, retry, or administrative result-email failure
never changes Reservation, Payment, Refund, LifecycleRequestHold, or the
lifecycle request.

## Acceptance Matrix

```text
1. Positive DATE_CHANGE automatically sends the guest payment link.
2. Positive STAY_EXTENSION automatically sends the guest payment link.
3. Guest copy states that requested dates are not effective until payment and successful completion.
4. Private button and plain-text fallback open the existing adjustment-payment page.
5. Guest SENT creates one administrative SENT result per configured admin.
6. Retryable guest failure does not create a premature administrative FAILED result.
7. Terminal guest FAILED creates one administrative FAILED result per configured admin.
8. Admin result text distinguishes provider acceptance from inbox delivery/opening.
9. Admin send button remains visible while the hold/link is usable.
10. Existing SENT history displays a duplicate warning.
11. PENDING/PROCESSING/retry-scheduled history displays an active-delivery warning.
12. Failed-only history does not display the duplicate warning.
13. Repeated manual submission with the same request UUID creates one child.
14. Manual resend preserves the original delivery row and audit history.
15. Worker reconciliation restores a missing automatic intent after a simulated post-commit interruption.
16. Zero-difference DATE_CHANGE omits additional-payment wording.
17. Negative DATE_CHANGE mentions a separate future refund confirmation without claiming completion.
18. Positive DATE_CHANGE retains the validated-additional-payment wording.
19. Email failure never rolls back request, hold, Payment, Reservation, or completed dates.
20. ES and EN HTML/plain-text output contains no raw provider, private token, or card data.
```
