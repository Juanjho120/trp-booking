## Purpose

Freeze the lifecycle-notification domain contract and add the typed persistence
relations required by later templates and orchestration.

This subphase does not render or send email. It prepares:

```text
- the complete eight-email scope;
- guest versus administrative audiences;
- authoritative event/source relations;
- permanent deduplication-key formats;
- exact future transaction boundaries;
- Prisma enum values, optional foreign keys, and indexes.
```

The accepted Phase 10 delivery, retry, test-recipient, manual-resend, and
administrative visibility foundation remains unchanged.

## Approved Email Scope

Phase 11.6 will implement eight automatic lifecycle emails.

| Notification type | Audience | Authoritative trigger |
| --- | --- | --- |
| `RESERVATION_CANCELLED` | Guest | Cancellation transaction commits |
| `ADMIN_RESERVATION_CANCELLED` | Admin recipients | Cancellation transaction commits |
| `RESERVATION_DATES_UPDATED` | Guest | `DATE_CHANGE` becomes `COMPLETED` |
| `ADMIN_RESERVATION_DATES_UPDATED` | Admin recipients | `DATE_CHANGE` becomes `COMPLETED` |
| `STAY_EXTENSION_CONFIRMED` | Guest | `STAY_EXTENSION` becomes `COMPLETED` |
| `ADMIN_STAY_EXTENSION_CONFIRMED` | Admin recipients | `STAY_EXTENSION` becomes `COMPLETED` |
| `REFUND_PROCESSED` | Guest | Refund reconciliation commits `APPROVED` |
| `ADMIN_REFUND_PROCESSED` | Admin recipients | Refund reconciliation commits `APPROVED` |

No notification is created merely because a request was recorded, approved,
rejected, withdrawn, expired, or failed. No refund notification is created for
`PENDING`, `PROCESSING`, inconclusive consult evidence, or `FAILED`.

## Guest and Administrative Boundaries

Guest messages use `Reservation.preferredLocale` and contain only the confirmed
business outcome needed by the guest.

Administrative messages use the configured admin locale and may include
protected operational context such as:

```text
- reservation and guest identity;
- lifecycle request type, channel, reason, actor, and completion time;
- original and requested dates/pricing;
- positive, zero, or negative financial-difference classification;
- linked adjustment Payment and lifecycle hold status;
- linked Refund authorization and reconciliation state;
- a protected reservation-detail URL.
```

Administrative templates must still exclude:

```text
- card number, CVV, expiration, or tokenized card data;
- Tilopay credentials, bearer tokens, API keys, or headers;
- raw provider payloads or unrestricted provider errors;
- secrets from arrival instructions;
- PMS-only operational data.
```

## Cancellation Notification Contract

`RESERVATION_CANCELLED` and `ADMIN_RESERVATION_CANCELLED` are created only when
the cancellation transaction commits:

```text
Reservation.status = CANCELLED
ReservationLifecycleRequest.requestType = CANCELLATION
ReservationLifecycleRequest.status = COMPLETED
```

The guest message confirms the cancellation outcome and may state the frozen
policy eligibility. It must not claim that money was returned.

When an eligible Refund is later reconciled as `APPROVED`, the separate
`REFUND_PROCESSED` pair is created.

## Date-Change Notification Contract

`RESERVATION_DATES_UPDATED` and `ADMIN_RESERVATION_DATES_UPDATED` are created
only when a `DATE_CHANGE` applies its requested dates/pricing and becomes
`COMPLETED`.

The contract covers:

```text
Positive difference
- exact adjustment Payment already APPROVED;
- lifecycle hold released;
- requested dates and pricing applied.

Zero difference
- no adjustment Payment;
- no lifecycle hold;
- requested dates and pricing applied.

Negative difference
- requested dates and pricing applied;
- exact lifecycle-adjustment Refund authorization may be PENDING;
- date-change email may describe a separate pending return;
- it must not claim the Refund was processed before APPROVED reconciliation.
```

The administrative version includes old/new dates, old/new totals, difference,
linked Payment/Refund identifiers when applicable, request channel, relevant
actors, completion time, and protected detail navigation.

## Stay-Extension Notification Contract

`STAY_EXTENSION_CONFIRMED` and `ADMIN_STAY_EXTENSION_CONFIRMED` are created only
when a specialized `STAY_EXTENSION` becomes `COMPLETED`.

The accepted domain invariant remains:

```text
- original check-in is preserved;
- requested check-out is later;
- only added nights are priced using current pricing;
- any positive difference is paid before completion.
```

The administrative version includes the preserved check-in, original/new
check-out, added nights, original total, added-night subtotal, new total, linked
adjustment Payment, lifecycle hold outcome, request channel, actors, completion
time, and protected detail navigation.

## Refund Notification Contract

`REFUND_PROCESSED` and `ADMIN_REFUND_PROCESSED` are created only in the
transaction that performs a real transition to:

```text
Refund.status = APPROVED
Payment.status = PARTIALLY_REFUNDED or REFUNDED
```

The same pair covers:

```text
- STANDARD_POLICY;
- EXTRAORDINARY;
- LIFECYCLE_ADJUSTMENT for a negative DATE_CHANGE;
- LIFECYCLE_ADJUSTMENT compensation after a paid positive mutation cannot commit.
```

The guest version confirms only the approved amount/currency and safe processing
guidance. It does not promise an unsupported bank-credit date.

The administrative version may include authorization type, processing mode,
reconciliation source, safe provider reference, affected Payment, resulting
financial status, authorizing/reconciling actors, related lifecycle request, and
protected detail navigation.

## Persistence Relations

`EmailNotification.reservationId` remains mandatory for every notification.

Phase 11.6.1 adds:

```text
EmailNotification.lifecycleRequestId String?
EmailNotification.refundId String?
```

Both relations use `ON DELETE SET NULL` because notification history must not
depend on destructive domain deletion. Existing rows remain valid and receive
`NULL` for both fields.

Expected link shapes:

```text
Cancellation guest/admin
- reservationId required
- lifecycleRequestId required
- refundId null

DATE_CHANGE guest/admin
- reservationId required
- lifecycleRequestId required
- refundId null

STAY_EXTENSION guest/admin
- reservationId required
- lifecycleRequestId required
- refundId null

STANDARD_POLICY refund guest/admin
- reservationId required
- refundId required
- lifecycleRequestId copied when the Refund is linked to the cancellation request

EXTRAORDINARY refund guest/admin
- reservationId required
- refundId required
- lifecycleRequestId normally null

LIFECYCLE_ADJUSTMENT refund guest/admin
- reservationId required
- refundId required
- lifecycleRequestId required
```

Future orchestration must validate that the Reservation, lifecycle request,
Refund, and Payment relationships agree before creating an intent. Foreign keys
alone do not prove that all linked rows belong to the same Reservation.

Manual resend rows must copy the source notification's `reservationId`,
`lifecycleRequestId`, and `refundId` while retaining their separate parent,
origin, requester, and deduplication key.

## Permanent Deduplication Keys

Recipients are trimmed and lowercased before key construction.

```text
reservation-cancelled/{lifecycleRequestId}/{recipient}
admin-reservation-cancelled/{lifecycleRequestId}/{recipient}

reservation-dates-updated/{lifecycleRequestId}/{recipient}
admin-reservation-dates-updated/{lifecycleRequestId}/{recipient}

stay-extension-confirmed/{lifecycleRequestId}/{recipient}
admin-stay-extension-confirmed/{lifecycleRequestId}/{recipient}

refund-processed/{refundId}/{recipient}
admin-refund-processed/{refundId}/{recipient}
```

One row is created per intended recipient. Multiple configured administrators
therefore receive separate rows and provider idempotency keys.

The new pure contract helper centralizes:

```text
- supported lifecycle notification types;
- guest/admin audience classification;
- lifecycle-request versus Refund source classification;
- recipient normalization;
- permanent key generation.
```

It does not read or write the database and does not call Resend.

## Future Transaction Points

The following boundaries are frozen for 11.6.3.

### Cancellation

Inside the existing Serializable transaction:

```text
Reservation -> CANCELLED
LifecycleRequest -> COMPLETED
arrival intent supersession
AdminAuditLog
guest EmailNotification upsert
one admin EmailNotification upsert per configured recipient
COMMIT
```

Delivery starts only after commit.

### DATE_CHANGE or STAY_EXTENSION

Inside the transaction that applies the final mutation:

```text
Reservation dates/pricing updated
LifecycleRequest -> COMPLETED
LifecycleRequestHold released when applicable
arrival intent supersession/replacement
AdminAuditLog
guest EmailNotification upsert
one admin EmailNotification upsert per configured recipient
COMMIT
```

Delivery starts only after commit.

### Refund

Inside the conclusive reconciliation transaction:

```text
Refund -> APPROVED
Payment -> PARTIALLY_REFUNDED or REFUNDED
AdminAuditLog
guest EmailNotification upsert
one admin EmailNotification upsert per configured recipient
COMMIT
```

Delivery starts only after commit.

A template, provider, retry, or delivery failure never reverses the accepted
Reservation, lifecycle request, Payment, Refund, hold, or audit transition.

## Historical Data and Backfill

```text
No automatic historical backfill.
```

Cancellation, date-change, extension, and Refund events completed before the
11.6 orchestration deployment remain visible in protected domain history but do
not automatically generate delayed emails.

This avoids surprising guests or administrators with messages for earlier test
or operational events.
