## Reason

Airbnb's current external-calendar import contract expects the imported calendar URL to end in `.ics`.

The accepted TRP export foundation uses:

```text
GET /api/ical/[token]
```

The route returns valid `text/calendar`, but the URL itself does not end in `.ics`.

Before connecting the first real TRP Test feed to Airbnb, TRP must therefore support:

```text
GET /api/ical/<RAW_PRIVATE_TOKEN>.ics
```

without changing token ownership, token hashes, outbound feed content, or the accepted 12.6.1 provider-loop-prevention contract.

## Implementation

The route still uses the existing `[token]` dynamic segment.

`normalizeAirbnbIcalExportPathToken()` accepts both:

```text
<TOKEN>
<TOKEN>.ics
```

For the `.ics` form, only the suffix is removed before the token is passed to `generateAirbnbIcalExportFeed()`.

Therefore the existing SHA-256 value remains valid:

```text
hash(<TOKEN>) = existing ExternalCalendar.exportTokenHash
```

The system does **not** hash:

```text
<TOKEN>.ics
```

No token rotation or database update is required.

## Compatibility Contract

The extensionless route remains available for operator diagnostics:

```text
/api/ical/<TOKEN>
```

The Airbnb-facing URL must use:

```text
/api/ical/<TOKEN>.ics
```

Both resolve to the same underlying private token and produce the same calendar content.

## Security

This correction does not change the fact that the raw token is a bearer credential carried in the request path.

After deploying 12.6.1.1:

```text
- access each .ics URL privately
- confirm HTTP 200 and text/calendar
- confirm the same expected VEVENT ranges/UIDs
- inspect Vercel Runtime Logs again
- stop if any raw token appears in logs
```

Do not paste raw tokens or complete private feed URLs into documentation, tickets, screenshots, commit history, or ChatGPT.
