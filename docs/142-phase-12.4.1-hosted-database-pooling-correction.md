## Observed Hosted Failure

After the stable Test deployment was connected to `trp-booking.juantzun.dev`, Vercel runtime logs intermittently showed Prisma server-side failures such as:

```text
PrismaClientUnknownRequestError
FATAL: (EMAXCONNSESSION) max clients reached in session mode
max clients are limited to pool_size: 15
```

The UI could consequently surface the generic server-side application error page while database-backed server components were loading.

The failing runtime was using the Supabase Session pooler for the Vercel `DATABASE_URL`.

## Root Cause

The Vercel application is serverless and can execute multiple isolated function instances. Session pooler mode reserves a backend connection for each client/session, which allowed the hosted workload to exhaust the configured pool client limit.

This was an environment/runtime connection mismatch, not a failure in the specific Prisma query shown in the log.

## Accepted Correction

Only the Vercel **Test** runtime connection was changed.

```text
DATABASE_URL
Before: Supabase Session pooler / port 5432
After:  Supabase/Supavisor Transaction pooler / port 6543
```

The runtime URL preserves the project database and TRP schema and applies the approved serverless connection-limiting parameters, including:

```text
schema=trp_booking
pgbouncer=true
connection_limit=1
```

`DIRECT_URL` was intentionally **not** replaced. It remains the separate direct/session-capable connection used for Prisma CLI and migration operations.

No Local/Test database split was introduced. Local and Test still use the same underlying developer-owned Supabase database.

## Acceptance Evidence

After saving the Vercel Production-environment `DATABASE_URL` and redeploying:

```text
- stable Test site loaded successfully
- admin navigation loaded successfully
- repeated navigation no longer reproduced EMAXCONNSESSION
- the previous max-clients server-side application errors stopped
- DIRECT_URL remained unchanged
- no application business logic changed
```

The owner confirmed the correction working on 2026-08-10.

## Google OAuth Observation During 12.4

Separate from the database correction, hosted OAuth validation established that the existing Local/Test Google OAuth Web Application client required both the stable callback and the stable JavaScript origin.

Preserved Local configuration:

```text
Authorized JavaScript origin:
http://localhost:3000

Authorized redirect URI:
http://localhost:3000/api/auth/callback/google
```

Added Test configuration:

```text
Authorized JavaScript origin:
https://trp-booking.juantzun.dev

Authorized redirect URI:
https://trp-booking.juantzun.dev/api/auth/callback/google
```

Hosted Google OAuth/admin login passed with `AUTH_TRUST_HOST=true`. No `AUTH_URL` override was required.
