## Goal

Apply authorized requested dates and requested pricing to the existing confirmed Reservation after the final server-side conditions are satisfied.

11.5.4 implements successful completion for:

```text
- Positive financial difference with one exact APPROVED LIFECYCLE_ADJUSTMENT Payment.
- Zero financial difference immediately inside the approval transaction.
```

The negative-difference branch and compensating refund for an approved payment whose completion cannot commit remain assigned to 11.5.5.

## Shared Completion Transaction

Both successful branches use one shared completion service and the same final validation contract:

```text
- Serializable transaction.
- Explicit 10-second maxWait and 20-second timeout.
- Up to three complete-transaction retries for Prisma P2034 only.
- Request type must be DATE_CHANGE or STAY_EXTENSION.
- Reservation must still be CONFIRMED.
- Reservation.updatedAt, current dates, guest count, prices, and currency must still match the immutable request snapshot.
- Property must remain active and supported.
- Requested dates, prices, guest count, and financial difference must be present and internally consistent.
- DATE_CHANGE must still be before the original and requested check-in moments.
- STAY_EXTENSION must retain the original check-in and complete before the current check-out boundary.
- Final availability validates the requested stay and its proposed preparation buffers.
- Availability excludes only the current Reservation and the current request's own LifecycleRequestHold.
- Every unrelated reservation, Airbnb event, manual block, maintenance block, preparation effect, composed dependency, and lifecycle hold remains blocking.
```

## Positive-Difference Completion

After Tilopay result validation marks the exact adjustment Payment APPROVED, the existing payment-confirmation boundary invokes the shared completion transaction.

Required state before completion:

```text
ReservationLifecycleRequest.status = AWAITING_ADJUSTMENT_PAYMENT
LifecycleRequestHold.status = ACTIVE
LifecycleRequestHold.expiresAt > completion time
Payment.purpose = LIFECYCLE_ADJUSTMENT
Payment.status = APPROVED
Payment.amount = exact positive financialDifference
Payment.currency = request currency
Payment.paidAt <= hold.expiresAt
```

Successful result:

```text
Reservation:
- Existing id preserved.
- status remains CONFIRMED.
- confirmedAt preserved.
- checkInDate/checkOutDate become the requested dates.
- subtotal/cleaningFee/taxes/discounts/total become the requested pricing snapshot.
- expiresAt remains untouched.

ReservationLifecycleRequest:
- status becomes COMPLETED.
- completedAt is set once.
- version increments.

LifecycleRequestHold:
- status becomes RELEASED.
- releasedAt is set.
- releaseReasonCode = LIFECYCLE_DATE_MUTATION_COMPLETED.
- version increments.

Payment:
- remains APPROVED and auditable.
- is never duplicated or downgraded.
```

Provider redirect replay invokes the same completion service and returns the already-completed result without moving dates twice.

## Zero-Difference Completion

Zero-difference approval and final completion occur inside the same existing admin Serializable transaction:

```text
PENDING_REVIEW
-> APPROVED
-> final availability/version validation
-> Reservation dates/prices applied
-> request COMPLETED
```

No Payment and no LifecycleRequestHold are created.

If any final validation fails, the entire approval transaction rolls back and the request remains PENDING_REVIEW with the original Reservation unchanged.

## Arrival Instructions

A successful completion:

```text
- Marks PENDING or FAILED ARRIVAL_INSTRUCTIONS tied to the old check-in snapshot as SKIPPED.
- Preserves SENT history.
- Creates one idempotent pending arrival-instruction intent for the new check-in when property instructions are complete and the new check-in is still in the future.
- Does not deliver email inside the completion transaction.
```

The lifecycle-specific emails `RESERVATION_DATES_UPDATED` and `STAY_EXTENSION_CONFIRMED` remain deferred to 11.6.

## Guest Adjustment Page

After a successful positive completion, the opaque payment page can render the `COMPLETED` state while its signed token remains valid:

```text
- No raw reservation, request, hold, or payment identifier is added to the URL.
- Checkout controls are hidden.
- The page confirms that the requested dates were applied.
- A completed request cannot create another payment attempt.
```

## Audit

Successful completion records:

```text
LIFECYCLE_DATE_CHANGE_COMPLETED
or
LIFECYCLE_STAY_EXTENSION_COMPLETED
```

A positive completion also records:

```text
LIFECYCLE_ADJUSTMENT_HOLD_RELEASED
```

Metadata includes bounded request/reservation IDs, trigger, original/requested dates, original/requested totals, difference, payment/hold IDs, reservation version, arrival-intent supersession, and an explicit flag that no lifecycle notification was created.
